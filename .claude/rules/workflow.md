# Работа с проектом

## Проверка перед пушем

```bash
./gradlew prePushCheck
```

Это `spotlessApply` (именно **применяет** форматирование, а не проверяет) и `detektDebug` с
разрешением типов, то есть заодно и компиляция. Тестов в нём нет — они запускаются отдельно:

```bash
./gradlew test
```

## Коммит по факту закрытия пункта плана

Пункт плана сделан — сразу коммит, без вопроса «закоммитить?». Пункт считается сделанным, когда код
написан, `prePushCheck` и `test` проходят и отметка в документе плана проставлена.

Коммиты разбиваются по слоям, а не сваливаются в один: новый модуль отдельно от проводки в сборку,
документ плана — третьим. Пуш остаётся по просьбе.

**Почему:** за работой следят по истории git, а не по рабочему дереву. Незакоммиченного там не видно
вовсе: новый модуль целиком прячется за одной строкой `?? lib/backend/`, и сделанная работа выглядит
как её отсутствие.

## Как пополнять правила

Правила лежат в `.claude/rules/` — по файлу на тему. Файл без `paths` во фронтматтере грузится
всегда, файл с `paths` — только когда в работе подходящий файл. Новая тема заводится новым файлом,
а не абзацем в чужом.

У каждого правила записана причина. Правило без причины переоткрывают на следующем ревью — и
переоткрывают верно, потому что защищать нечего.

Новое правило появляется здесь только с явного «да» владельца проекта на конкретную формулировку.
Замеченный кандидат предлагается в чате готовым текстом и ждёт ответа.

**Почему:** правило, записанное самостоятельно, следующая сессия исполняет уверенно и молча —
включая случаи, где оно было домыслом. Неверное правило хуже отсутствующего.
