# SQLDelight (`.sq`)

## Порядок запросов

Схема (таблица, индексы) — выше всех. Дальше запросы по виду операции: чтение, добавление,
изменение, удаление. Внутри группы порядок правилом не задаётся.

**Почему:** к файлу таблицы приходят с вопросом «что отсюда можно достать» — чтения должны стоять
сразу под схемой. Разрушительные операции стоят последними и не попадаются на глаза первыми.

Перестановка даёт крупный дифф при неизменившемся смысле — такую правку держать отдельно от
содержательных.

## Имена запросов

Имя не содержит имени таблицы и не пересказывает сигнатуру: `selectItemsByOrder` → `selectByOrder` →
`select`, если параметр и так один. Различающий суффикс несёт смысл — потребителя или полноту
проекции: `selectWithEmail` плохо, `selectShort` / `selectForCatalog` хорошо.

**Почему:** таблица уже названа файлом и сгенерированным классом. Имя вокруг одной колонки
устаревает при добавлении второй и превращается в `selectWithEmailAndPhone`.

Повисший предлог не суффикс: `deleteBy` без объекта не лучше `delete`.

## Порядок колонок и порядок ключа — разные решения

В `CREATE TABLE` колонки идут от первостепенных к второстепенным: собственный идентификатор строки,
затем внешние ключи и атрибуты. В составном `PRIMARY KEY` первой стоит та колонка, по которой
фильтрует большинство запросов.

**Почему:** это разные оси. Список колонок описывает состав строки, `PRIMARY KEY` описывает индекс:
колонка, не стоящая первой, не может служить префиксом, и фильтрация уходит в полное сканирование.
Уникальность от перестановки ключа не меняется — поэтому «выровнять ключ под порядок колонок»
выглядит косметикой и молча стоит производительности.

## Типизированные id-колонки

Колонка с идентификатором объявляется через `AS` с доменным типом: `branchId TEXT AS Branch.Id NOT
NULL`, коллекция — `approvedByIds TEXT AS Set<UserId> NOT NULL`. Сырой `TEXT` остаётся у настоящих
строк — имя, текст сообщения.

**Почему:** сырой `TEXT` заставляет каждый вызов разворачивать тип, а каждый маппер — заворачивать
обратно, и компилятор не ловит, если в запрос по ветке передали id коммита: обе стороны `String`.

- Адаптер — `object` в `database/adapter/`, один тип на файл; проводка в `DatabaseModule`.
- Дженерик пишется прямо в `AS`, typealias не нужен — достаточно `import kotlin.collections.Set;`.
- Граница с Firestore не затрагивается: в `*NM`-моделях поля остаются сырыми `String` и сохраняют
  имена полей бэкенда (`initiatorUid`, `approvedByUids`).

## Составное значение — одной колонкой

Набор полей, существующий только целиком, занимает одну колонку с адаптером: `TEXT AS Some.Value`.
Раскладывать его на набор nullable-колонок нельзя.

**Почему:** набор nullable-колонок не даёт схеме удержать инвариант «либо все поля, либо ни одного».
Инвариант переезжает в Kotlin и превращается в `if (a != null && b != null && …)` в каждом маппере.

Исключение — когда по полям значения нужны SQL-запросы (фильтр, join, индекс): тогда отдельная
таблица с `NOT NULL`-колонками.

## Квалификация колонок, без алиасов

Алиасы таблиц (`FROM Item AS i`) не использовать. Нужен префикс или нет — решает число таблиц в
запросе, а не происхождение колонки: одна таблица — колонки голые, две и больше — префикс у **всех**,
включая колонки основной таблицы.

**Почему:** алиас читается как сущность, которой в схеме нет. Голая колонка в джойне — молчаливое
утверждение «она из основной таблицы», проверить которое можно, только помня обе схемы наизусть.

- Правило сквозное по запросу: выборка, `ON`, `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`.
- Подзапрос — своя область; ссылка наружу квалифицируется всегда, именно она делает его
  коррелированным.
- Единственный неизбежный алиас — self-join.
- `AS` над колонкой (имя поля в проекции) правилом не затрагивается.

## `ON` с новой строки

`JOIN <таблица>` — своя строка, `ON <условие>` — следующая, с отступом. Условие остаётся одной
строкой, сколько бы частей через `AND` в него ни входило.

**Почему:** имена таблиц выстраиваются по левому краю в столбик (`FROM`, `JOIN`, `JOIN`) — состав
запроса читается сверху вниз одним взглядом. Перенос делается всегда, даже когда условие короткое:
исключение вернуло бы вилку «можно так, можно эдак».

## Состав данных — в столбик

Перечисление, задающее **состав данных**, пишется по элементу на строку — в том числе когда элемент
один: колонки `INSERT`, список `VALUES`, выборка `SELECT`, присваивания `UPDATE … SET`, объявление
колонок `CREATE TABLE`.

В строку остаются обвязка и способ подачи: ограничения таблицы, колонки индекса, список в `IN`,
`WHERE`, `ORDER BY`, `GROUP BY`.

**Почему:** состав данных сверяют с таблицей и с сигнатурой вызова, и правят добавлением и удалением.
Вертикальный список делает каждый элемент отдельной строкой диффа. Исключение для одного элемента
убивает выгоду: как только колонок становится две, запрос переформатируется и правка тонет в шуме.

Открывающая скобка остаётся на строке с тем, к чему относится, закрывающая — на своей. `*` не
перечисление и в столбик не разворачивается.

## Значения `INSERT` — явно и поимённо

На каждую колонку свой именованный параметр. Подстановка всей строки одним параметром не
используется, анонимный `?` в списке значений не оставляется. Имя параметра совпадает с именем
колонки — тогда списки колонок и значений читаются построчно парой.

**Почему:** одиночный параметр заставляет вызывающего собирать готовую строку таблицы, хотя ему нужно
просто передать значения. Столбик анонимных `?` не сообщает ничего: соответствие колонке приходится
восстанавливать, считая позиции в двух списках, и вставленная в середину колонка ломает этот счёт
молча.

Плата известна и принята: вызывающий код, у которого строка уже собрана в объект, разбирает её по
полям вручную. Обходить правило хелпером, принимающим строку целиком, нельзя.

Условия (`WHERE … = ?`, `IN ?`) правило не затрагивает.
