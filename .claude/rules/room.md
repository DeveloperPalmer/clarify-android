# Room

## Наблюдаемый запрос — только `DistinctFlow`

Метод DAO, на который подписываются, возвращает `DistinctFlow<T>`, а не `Flow<T>`. Разовое
чтение — `suspend`. Имя говорит, какой из двух: `observe…` или `select…`.

**Почему:** Room перевыпускает результат на любую запись в таблицы запроса, даже если выборка не
изменилась. Повтор, попавший в `flatMapLatest { remoteListener(...) }`, пересоздаёт слушатель
Firestore — так уже сгорела дневная квота за минуты; попавший в состояние Compose, раздувает
`SnapshotIdSet`. `DistinctFlow` строится только конвертером и всегда дедуплицирует: гарантия видна
в сигнатуре, а `Flow<T>` в DAO — заметное на ревью нарушение.

## Родителя не пишут заменой

Таблицу, на которую ссылаются внешние ключи, пишут через `@Query` с
`INSERT … ON CONFLICT (id) DO UPDATE SET`. `@Insert(onConflict = REPLACE)`, `INSERT OR REPLACE` и
`@Upsert` — только для таблиц без детей. Поля, которые ведутся локально, в `SET` не входят.

**Почему:** Room включает внешние ключи, а замена — это удаление и вставка: каскад молча уносит
детей вместе с родителем. `ChatDatabaseForeignKeysTest` показывает это на одной и той же строке.
Локальное поле в `SET` обнулялось бы каждой записью с сервера — так сбрасывался бы `unreadCount`.

## Типизированные id и составное значение

Поле сущности и параметр DAO с идентификатором — доменного типа (`Branch.Id`, `UserId`); сырой
`String` остаётся у настоящих строк. `value class` Room разворачивает сам; для `data class` и для
составного значения пишется `@ColumnTypeConverter` — `object` в `converter/`, один тип на файл.
Значение, существующее только целиком, занимает одну колонку.

**Почему:** с сырым `String` компилятор не заметит id коммита в запросе по ветке. Набор
nullable-колонок не держит инвариант «все поля или ни одного» — проверка расползается по мапперам.

- Исключение — когда по полям значения нужны SQL-запросы (фильтр, join, индекс): тогда отдельная
  таблица с `NOT NULL`-колонками.
- Граница с Firestore не затрагивается: в `*NM`-моделях поля остаются сырыми `String` и сохраняют
  имена полей бэкенда (`initiatorUid`, `approvedByUids`).

## Порядок полей и порядок ключа — разные решения

Поля сущности идут от первостепенных к второстепенным; в составном `primaryKeys` первой стоит
колонка, по которой фильтрует большинство запросов.

**Почему:** поля описывают состав строки, ключ — индекс. Колонка, не стоящая в ключе первой, не
служит префиксом, и фильтр по ней уходит в полное сканирование. «Выровнять ключ под порядок
полей» выглядит косметикой и молча стоит производительности.

## Порядок методов DAO

Методы идут по виду операции: чтение, добавление, изменение, удаление. Внутри группы порядок
правилом не задаётся.

**Почему:** к DAO приходят с вопросом «что отсюда можно достать» — чтения должны стоять первыми.
Разрушительные операции стоят последними и не попадаются на глаза первыми.

Перестановка даёт крупный дифф при неизменившемся смысле — такую правку держать отдельно от
содержательных.

## Имена методов DAO

Имя не содержит имени таблицы и не пересказывает сигнатуру: `selectItemsByOrder` → `selectByOrder` →
`select`, если параметр и так один. Различающий суффикс несёт смысл — потребителя или полноту
проекции: `selectWithEmail` плохо, `selectShort` / `selectForCatalog` хорошо.

**Почему:** таблица уже названа DAO. Имя вокруг одной колонки устаревает при добавлении второй и
превращается в `selectWithEmailAndPhone`.

Повисший предлог не суффикс: `deleteBy` без объекта не лучше `delete`.

## Квалификация колонок, без алиасов

Алиасы таблиц (`FROM Item AS i`) не использовать. Нужен префикс или нет — решает число таблиц в
запросе, а не происхождение колонки: одна таблица — колонки голые, две и больше — префикс у **всех**,
включая колонки основной таблицы.

**Почему:** алиас читается как сущность, которой в схеме нет. Голая колонка в джойне — молчаливое
утверждение «она из основной таблицы», проверить которое можно, только помня обе схемы наизусть.

- Правило сквозное по запросу: выборка, `ON`, `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`.
- Подзапрос — своя область; ссылка наружу квалифицируется всегда, именно она делает его
  коррелированным.
- Единственный неизбежный алиас — self-join.
- `AS` над колонкой (имя поля в проекции) правилом не затрагивается.

## `ON` с новой строки

`JOIN <таблица>` — своя строка, `ON <условие>` — следующая, с отступом. Условие остаётся одной
строкой, сколько бы частей через `AND` в него ни входило.

**Почему:** имена таблиц выстраиваются по левому краю в столбик (`FROM`, `JOIN`, `JOIN`) — состав
запроса читается сверху вниз одним взглядом. Перенос делается всегда, даже когда условие короткое:
исключение вернуло бы вилку «можно так, можно эдак».

## Состав данных — в столбик

Перечисление, задающее **состав данных**, пишется по элементу на строку — в том числе когда элемент
один: колонки `INSERT`, список `VALUES`, выборка `SELECT`, присваивания `UPDATE … SET`.

В строку остаются обвязка и способ подачи: колонки индекса, список в `IN`, `WHERE`, `ORDER BY`,
`GROUP BY`.

**Почему:** состав данных сверяют с таблицей и с сигнатурой вызова, и правят добавлением и удалением.
Вертикальный список делает каждый элемент отдельной строкой диффа. Исключение для одного элемента
убивает выгоду: как только колонок становится две, запрос переформатируется и правка тонет в шуме.

Открывающая скобка остаётся на строке с тем, к чему относится, закрывающая — на своей. `*` не
перечисление и в столбик не разворачивается.

## Значения `INSERT` в `@Query` — явно и поимённо

На каждую колонку свой именованный параметр, анонимный `?` в списке значений не оставляется. Имя
параметра совпадает с именем колонки — тогда списки колонок и значений читаются построчно парой.

**Почему:** столбик анонимных `?` не сообщает ничего: соответствие колонке приходится
восстанавливать, считая позиции в двух списках, и вставленная в середину колонка ломает этот счёт
молча.

Строка целиком пишется через `@Insert` с сущностью — это способ Room, а не обход правила. `@Query`
со вставкой остаётся там, где нужен SQL, которого `@Insert` не выразит: `ON CONFLICT … DO UPDATE`.

Условия (`WHERE … = ?`, `IN (…)`) правило не затрагивает.
