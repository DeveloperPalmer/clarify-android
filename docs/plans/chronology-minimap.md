# Мини-карта хронологии — документ решения

Проектирование **уровня 1**: разведка по исходникам, один проект, самокритика по трём линзам.
Уровень выбран до разведки и по её итогам не пересматривался: односторонних решений здесь нет,
каждое обратимо правкой одной функции, а вся арифметика проверяется на JVM. Раунда с несколькими
проектами и судейством, как у инерции и зума, задача не требует.

Документ самодостаточен: его читает сессия, которая берёт задачу с нуля и переписки не видела.
Контекст фичи — в [chronology-log.md](chronology-log.md), дизайн — в
[chronology-design-prompt.md](chronology-design-prompt.md).

## 1. Требование

Дословно, словами владельца:

> Мы можем на данном этапе реализовать мини карту? Выглядит так что ее лучше сразу реализовать

И далее, после разбора двух развилок: «Со всеми предложениями согласен. Приступаем к
проектированию мини карты».

Спека — §11.1 брифа:

> **Мини-карта** — полоса 48 dp внизу: вся история сжато плюс перетаскиваемая рамка вьюпорта.
> Ветки на ней — короткие цветные засечки. При перетаскивании над пальцем всплывает пузырь с
> датой — это заодно закрывает задачу «перейти к дате» без датапикера, которого в проекте нет.

Плюс §11.3: «Перетаскивание рамки мини-карты · быстрая навигация · конфликт с паном полотна ·
мини-карта перехватывает жест целиком» и решение прототипа v2 №5 (§18): «Мини-карта — часть каждого
экрана графа, а не отдельный режим: полоса 48 dp внизу везде, пузырь даты появляется только при
перетаскивании рамки».

### Зафиксировано владельцем в этом заходе

1. **Мини-карта и отладочная панель делят низ экрана.** Панель садится **над** мини-картой, а
   полотно учится принимать несколько зон жеста вместо одной. Мини-карта остаётся на месте всегда.
2. **Минимальная ширина рамки — 32 dp.** Рамка перестаёт быть честной пропорцией, зато остаётся
   управляемой. Альтернатива («оставить пропорцию честной, ловить скраб по всей полосе») отклонена
   как замена; скраб по всей полосе при этом введён отдельно — см. §4.

### Границы объёма

Не входит: реальные данные вместо демо-набора, статус ветки на засечке, вертикальная навигация
мини-картой, анимированный перелёт камеры, сохранение позиции при повороте
(`rememberSaveable` отложен журналом отдельно).

### 2.2 Арифметика демо-набора, из которой всё следует

Демо — 22 узла на 14 дорожках (`screen/chronology/Mocks.kt`), плашка эпизода 200 dp
(`EpisodeNode.kt:71`), поля полотна 64 dp (`GraphGeometry.kt:250`), зазоры 40/68/96/124/152 dp
(`mapper/TimeGapMappers.kt`).

Сумма зазоров 2056 dp, сумма ширин 4400 dp, правый край последней плашки 6456 dp,
`bounds.x = [32, 6520]`, ширина содержимого **6488 dp**, `centreSpanX = [196, 6356]`.

Экран взят 412 dp шириной; полоса мини-карты — экран минус внешний отступ 12 dp и внутреннее поле
8 dp с каждой стороны, то есть **трек 372 dp**.

| Масштаб | Видимое окно, dp полотна | Честная доля рамки | Рамка на треке | Насыщение у каждого края |
|---|---|---|---|---|
| 0.4× | 1030 | 15.88 % | 59.1 dp | 5.41 % трека (20 dp) |
| 0.572× | 720 | 11.10 % | 41.3 dp | 3.02 % |
| 0.738× | 558 | 8.60 % | **32 dp — порог** | 1.77 % |
| 1× | 412 | 6.35 % | 23.6 dp → 32 dp | 0.65 % |
| 1.5× | 275 | 4.23 % | 15.7 dp → 32 dp | 0 % |
| 2.5× | 165 | 2.54 % | 9.4 dp → 32 dp | 0 % |

Три числа, которые задают весь проект:

1. **Выше 0.738× рамка упирается в минимум 32 dp** и перестаёт быть честной пропорцией. Это не
   краевой случай, а две трети рабочего диапазона.
2. **9.4 dp** — вот чем была бы рамка на 2.5× без минимума. Пальцем это не берётся, и решение
   владельца про 32 dp разведкой подтверждается, а не переоткрывается.
3. **Насыщение**: камере разрешено уезжать дальше краёв содержимого, потому что диапазон — это
   объединение двух политик (GraphCamera.kt:108–140). На 0.4× достижимая область полотна
   `[−319, 6871]` против `bounds [32, 6520]`: 5.41 % трека с каждой стороны камера гуляет, а рамка
   уже стоит у края. На 1.5× и выше расхождения нет вовсе.

На короткой переписке минимума не возникает: пять эпизодов дают `bounds` 1512 dp, рамка на 1× —
27.2 % трека, то есть 101 dp. Минимальная ширина работает только там, где история длинная, — и это
ровно то, ради чего она заведена.

### 2.3 Чего в коде нет и что придётся приблизить

- **Веток как сущностей не существует.** `GraphNode` знает только дорожку и паузу
  (`entity/GraphNode.kt`). Засечки собираются из первого по времени узла каждой дорожки, отличной
  от нуля.
- **Статус ветки мини-карте недоступен.** Флаг `dim` («эпизод внутри слитой ветки») живёт в
  `EpisodeContent`, то есть в содержимом плашки, а не в раскладочной модели. Тащить его в
  `GraphNode` ради засечки — значит завести в раскладочной сущности поле, на раскладку не влияющее.
- **Дата берётся из строк демо-набора** (`EpisodeContent.time`), потому что домена ещё нет.
  Компонент принимает её параметром, поэтому переход на настоящие данные его не заденет.
- **`placement` наружу не отдаётся** — только `edges` и отладочный `debugInfo`. Значит перевод
  «камера → доля полосы» обязан жить в держателе состояния и отдаваться как `State`.

## 3. Дефекты существующего кода, которые чинятся первыми

### 3.1 Слот `overlay` принимает ровно одну зону

`GraphCanvas` держит `var panelBounds by remember { mutableStateOf(Rect.Zero) }`
(GraphCanvas.kt:80) и отдаёт слоту один обработчик. Двух инструментов у нижнего края этот механизм
не выдерживает: второй затрёт зону первого.

Объединить обе зоны в один прямоугольник нельзя — не по эстетике, а потому что объединение
захватывает полосу графа между панелью и мини-картой и **заработает случайно**: пока инструменты
смежны, ложь незаметна, а первый же отступ между ними отдаст графу жесты, которые тот не должен
брать, либо наоборот.

### 3.2 Зона объявляется в координатах родителя, а не полотна

`GraphDebugOverlay` отдаёт `it.boundsInParent()` (GraphDebugOverlay.kt:145), а полотно сравнивает
эту зону с позицией касания, которая приходит в координатах **его собственного** `Box`
(GraphCanvas.kt:95). Сегодня это совпадает ровно потому, что панель — прямой ребёнок этого `Box`.

Мини-карта и панель встают в общую `Column` у нижнего края (иначе появление панели двигало бы
мини-карту, а §11.1 требует, чтобы она стояла на месте всегда). С этого момента `boundsInParent()`
возвращает координаты внутри `Column`, и зона уезжает на её смещение — жест начнёт проходить сквозь
панель к графу.

**Это дефект, ломающийся молча**: компилятор не заметит, тест не упадёт, а на устройстве граф
поедет под пальцем, положенным на панель, — ровно та неисправность, ради которой зоны и заводились
(итерация 25 журнала).

Лечение: зоны объявляются в координатах корня (`boundsInRoot()`), а полотно переводит в них позицию
касания, зная собственное положение в корне. Одно определение системы координат на обе стороны.

### 3.3 Скраб не остановит инерцию сам

Жест полотна зовёт `stopFling()` на касании (GraphCanvas.kt:96), но жест, начатый **внутри** зоны,
до полотна не доходит вовсе (GraphGesture.kt:60). Значит палец, опущенный на мини-карту во время
затухания, инерцию не оборвёт, и бросок будет драться со скрабом за камеру.

Лечение бесплатное: скраб идёт через `pan()`, который сам зовёт `stopFling()`
(GraphCanvasState.kt:164). Это не деталь реализации, а причина не заводить для скраба отдельный
путь записи камеры.

## 4. Решение

> **Правка по итогам первой проверки руками.** §4.1 и §4.2 ниже описывают решение, которое не
> пережило устройства: у каждого края полосы набегало от 16 до 29.5 dp, где палец едет, а граф уже
> стоит. Действующая арифметика — в §4.1а; §5 переписан под неё. Остальные разделы в силе.

### 4.1а Действующая арифметика: положение — доля хода

Мир полосы — **отрезок центров крайних плашек** (`centreSpanX`), а не `bounds`. Камера упирается
тогда, когда в центре экрана стоит центр крайней плашки, поэтому мир, растянутый до краёв полей
полотна, отдавал под ход 2.5 % полосы у каждого края, которых у камеры нет.

Положение рамки — доля **хода**, и на полосу она ставится так:

```
left = position · (полоса − ширина рамки)
centre = left + ширина рамки / 2
```

Ход рамки тем самым сам подстраивается под её ширину: чем крупнее масштаб, тем рамка уже, тем
длиннее её ход и тем больше графа проезжает за каждый пиксель. Края совпадают с упорами камеры на
любом масштабе, включая те, где рамка расширена до 32 dp. Обратно — палец задаёт середину рамки:

```
position = (доля полосы под пальцем − ширина рамки / 2) / (1 − ширина рамки)
```

Засечки размечаются **той же** формулой `trackCentreOf`, поэтому «рамка накрывает засечку центром»
означает «ветка в центре экрана» — то самое движение, ради которого мини-карта существует.

Числа на демо-наборе (полоса 372 dp, экран 412 dp, мир 6328 dp):

| Масштаб | Рамка | Ход рамки | Мёртвый ход у краёв |
|---|---|---|---|
| 0.4× | 60.5 dp | 311.5 dp | 0 / 0 |
| 0.777× | 32 dp — порог | 340 dp | 0 / 0 |
| 1× | 32 dp | 340 dp | 0 / 0 |
| 2.5× | 32 dp | 340 dp | 0 / **4.4 dp** |

Остаток на 2.5× — от политики диапазона: выше масштаба 1.256 границы камеры задаёт уже край
содержимого, а не центр крайней плашки. Убрать и его можно, только сделав миром достижимую область
камеры, — но она зависит от масштаба, и засечки поехали бы под пальцем во время зума.

### 4.1 Мини-карта — карта, а не скроллбар (заменено, см. §4.1а)

Полоса показывает **фиксированный мир** — `bounds` содержимого. Мир не зависит от масштаба:
засечка ветки стоит на одном и том же месте полосы и при 0.4×, и при 2.5×.

Отвергнутая альтернатива — мир как «всё, куда достаёт камера». Она даёт биекцию без насыщения, но
мир начинает дышать при пинче: по числам §2.2 первая плашка переезжает с 2.5 % полосы на 7.2 %, то
есть на 18 dp, — засечки поедут под пальцем во время зума. Карта, у которой метки ползают при
масштабировании, перестаёт быть картой.

Вторая отвергнутая альтернатива — скроллбарная арифметика «доля хода камеры», где рамка ходит по
треку от нуля до `трек − ширина рамки`. Она идеально дружит с минимальной шириной, но у неё нет
общей системы координат с засечками: узел на середине истории не окажется под центром рамки. А
именно это движение — «тащу рамку к цветной засечке, чтобы попасть в ветку» — и есть то, ради чего
мини-карта существует.

### 4.2 Прямое и обратное преобразование (заменено, см. §4.1а)

Обе функции работают **через центр рамки**, а не через её левый край. Это снимает вопрос
минимальной ширины целиком: расширение рамки до 32 dp симметрично относительно центра, а обратная
функция о ширине вообще не знает.

Прямое (камера → полоса), в долях `[0, 1]`:

```
centre = (viewport.width / 2 − camera.x) / scale      // точка полотна в центре экрана
u      = (centre − bounds.left) / bounds.width        // доля мира
width  = (viewport.width / scale) / bounds.width      // честная доля рамки, не больше 1
left   = (u − width / 2) зажатое в [0, 1 − width]
```

Обратное (полоса → камера):

```
centre  = bounds.left + u · bounds.width
camera.x = viewport.width / 2 − centre · scale, зажатое диапазоном cameraRangeOf(...)
```

Зажатие обратной функции диапазоном — не страховка, а само определение: диапазон камеры и есть
единственная истина о том, где ей можно быть (`cameraRangeOf`, канон «одно определение понятия»).

**Расширение до 32 dp делает не камера, а инструмент.** Минимум задан пальцем, а не содержимым,
поэтому чистая функция отдаёт честную долю, а мини-карта в фазе рисования расширяет её вокруг того
же центра, зная ширину своего трека. Камера от этого не меняется — расширенная рамка остаётся
честным указателем на центр.

### 4.3 Скраб ловится по всей полосе, а не только по рамке

Касание в любой точке полосы ставит центр рамки под палец, дальнейшее движение ведёт её за пальцем.
Причина: по числам §2.2 рамка на 2.5× занимает 2.5 % трека честной ширины, и требование «попади
сначала в рамку» вернуло бы ровно ту проблему, ради которой заведён минимум 32 dp. Ровно так же
устроены мини-карты в редакторах и полоса прокрутки в IDE.

Ни инерции, ни анимации у скраба нет. Инерция на полосе означала бы пролёт истории после
отпускания — движение, которого пальцем не задавали. Анимация перелёта рассинхронизировала бы
рамку с пальцем на следующем же кадре движения.

### 4.4 Навигация только по времени

Скраб двигает камеру по X и не трогает Y. Причина арифметическая: 14 дорожек демо-набора в полосе
48 dp дают 3.4 dp на дорожку — различить их нельзя, а рамка, честная по обеим осям, стала бы
прямоугольником высотой 3 dp. Вертикаль остаётся за паном, где она и работает.

Наводить Y «умно» — на ближайший узел после скраба — сознательно не делаем: это подменяет прямое
манипулирование догадкой, и пользователь теряет то место по вертикали, где стоял.

### 4.5 Что рисует полоса

Высота 48 dp (§11.1), подложка `cardPrimary` через `Modifier.surface` с `round12` и
`elevation.large` — тем же языком, что и отладочная панель, чтобы низ экрана не выглядел из двух
разных приложений.

Внутри полосы:

- **линия магистрали** — 1 dp `contentQuaternary` по центру полосы во всю ширину трека;
- **засечки веток** — вертикальные штрихи 2 dp шириной и 12 dp высотой, вверх от линии для дорожек
  выше магистрали, вниз — для дорожек ниже. Цвет — идентичность дорожки;
- **рамка вьюпорта** — `drawRoundRect` со скруглением 8 dp: заливка `contentAccentPrimary` @ 12 %,
  обводка `Stroke(1.5 dp)` тем же цветом. Акцент здесь законен: §3.2 брифа запрещает акцент как
  цвет **текста** на тёмном, а заливки и обводки разрешает прямо;
- **пузырь даты** — только во время скраба, над полосой, `cardPrimary` + `elevation.medium`, текст
  `caption` `contentSecondary`, появление и исчезновение — `smallTween` (150 мс).

**Цвет идентичности дорожки** — `graphLane1…6` по формуле `floorMod(lane, 6)`, магистраль (`lane 0`)
— `contentTertiary`. Формула выбрана из-за одного свойства: соседние дорожки **никогда** не получают
один цвет, потому что разность их номеров равна единице. Повтор через шесть дорожек неизбежен — их
14, а оттенков 6 — и допустим: бриф §7 просит 4–6 оттенков идентичности.

**Статус ветки на засечке не кодируется.** Это прямое следствие §7 брифа: цвет — идентичность,
статус — паттерн штриха и терминатор. На засечке 2 × 12 dp паттерна нет, значит нет и статуса. Плюс
`dim` мини-карте и не доступен (§2.3).

### 4.6 Где живёт что

| Что | Где | Почему там |
|---|---|---|
| `viewportSpanOf`, `scrubbedCameraXOf`, `laneMarksOf`, `widenedSpanOf` | новый `components/canvas/GraphMinimapGeometry.kt` | одна тема — перевод между камерой и полосой; знает про камеру, но камера про неё не знает |
| `GraphViewportSpan`, `GraphLaneMark` | `ui/entity/` | правило «один класс — один файл», сущности в `entity` своего модуля |
| `Int.toLaneColor()` | `ui/mapper/GraphLaneMappers.kt` | правило «мапперы — в пакет `mapper`»; потребителей будет трое: мини-карта, глифы обзора, типизированные рёбра |
| `GraphMinimap` | `components/canvas/GraphMinimap.kt` | инструмент полотна, там же, где отладочная панель |
| `nearestCentreIndexOf` | `components/canvas/GraphGeometry.kt` | «какая плашка ближе к этой точке» — вопрос о раскладке, а не о камере |

### 4.7 Держатель состояния

`GraphCanvasState` получает три новых `State` и один метод. Наружу — только `State`, читаются в
своей фазе (правило `.claude/rules/compose.md`).

```kotlin
/** Какая доля содержимого по времени видна сейчас: доли [0, 1]. Читать в фазе рисования. */
val viewportSpan: State<GraphViewportSpan>

/** Начала дорожек в долях содержимого. Меняются только с раскладкой. */
val laneMarks: State<List<GraphLaneMark>>

/** Узел, ближайший к центру экрана по времени: подпись пузыря. Читать в листе. */
val centralNode: State<GraphNode.Id?>

/** Наводит центр экрана на долю [fraction] содержимого. */
fun scrubTo(fraction: Float)
```

Три решения внутри:

1. **`scrubTo` идёт через существующий `pan()`**, вычислив дельту до целевой камеры. Даром
   достаются: обрыв инерции (§3.3), кламп на записи, параллакс фона на потреблённое, `isMoved`,
   счётчик `pan` в телеметрии. Второй путь записи камеры разошёлся бы с этим при первой правке.
2. **Все три `State` — `derivedStateOf`.** `centralNode` возвращает `GraphNode.Id`, поэтому
   `derivedStateOf` гасит покадровые изменения: пузырь рекомпонуется при смене узла, а не при
   каждом кадре скраба.
3. **Ни одна сущность не называется «мини-картой».** `viewportSpan` — факт о камере («какая часть
   истории видна»), а не о том, кто его показывает. Состояние про мини-карту не знает, ровно как не
   знает про отладочную панель.

### 4.8 Зоны жеста

`GraphCanvas` держит `mutableStateMapOf<Any, Rect>` вместо одного `Rect`, слот получает
`(key: Any, bounds: Rect) -> Unit`, снятие — тем же вызовом с `Rect.Zero` либо удалением ключа на
`onDispose`. Позиция касания переводится в координаты корня прибавлением собственного положения
полотна, которое оно узнаёт из `onGloballyPositioned` на своём `Box`.

Модификатор-регистратор (`Modifier.graphOverlayZone(...)`) отвергнут: снятие зоны при уходе с
композиции потребовало бы своего `ModifierNodeElement` — первого в проекте — ради двух потребителей.
Колбэк с ключом даёт то же самое механизмами, которые в фиче уже работают.

## 5. Чем платим

1. **Рамка почти всегда не пропорция, а хват.** Выше 0.777× ширина упирается в 32 dp; на 2.5×
   честные 10 dp показаны как 32 — рамка втрое шире правды. Обратный ход: уменьшить минимум до
   24 dp, если на устройстве хват окажется избыточным.
2. **Засечки сдвигаются при зуме.** Они размечаются ходом рамки, а ход зависит от её ширины: у краёв
   полосы засечка переезжает на 15 dp при зуме от 0.4× к единице, в середине не двигается вовсе.
   Это плата за то, что края полосы точно совпадают с упорами камеры; обратный размен — §4.1а.
3. **Остаточный мёртвый ход 4.4 dp** у дальнего края на 2.5×: выше масштаба 1.256 диапазон камеры
   задаёт край содержимого, а не центр крайней плашки.
3. **Вертикаль мини-картой не управляется.** После скраба пользователь может оказаться на пустой
   полосе между дорожками — ровно там, где он был по вертикали до скраба.
4. **Скраб привязан к доле, а не к дельте.** Сообщение, пришедшее во время жеста, растит `bounds` —
   и содержимое под пальцем сдвигается. Величина сдвига не больше ширины нового узла с зазором
   (до 352 dp полотна, то есть до 5 % трека), случай редкий. Снимать `bounds` на старте жеста
   нельзя: тогда за длинный скраб рамка разъедется с содержимым.
5. **Поиск ближайшего узла линейный** — O(n) на кадр скраба. На 22 узлах это ничто; при
   виртуализации заменяется бинарным поиском по отсортированному массиву центров. Опираться на
   монотонность `centres` сейчас нельзя: канон говорит, что агрегат не должен зависеть от
   совпадения порядка узлов с порядком по оси.
6. **В отладочной панели скраб неотличим от протяжки** — он и идёт через `pan`. Отдельная фаза
   `scrub` не заводится: панель считает вызовы, а не величину, и всплеска скраб не даст.
7. **Семантика ползунка — первое применение в проекте.** Сейчас есть ровно один
   `semantics { role = Role.Button }` (uikit `component/button/Buttons.kt:267`) и один
   `contentDescription`. Закладывать время на `progressBarRangeInfo` + `setProgress` +
   `contentDescription`, а не считать бесплатным.
8. **Мир включает поля полотна.** `bounds` раздут на 64 dp с каждой стороны плюс системные врезки
   (`canvasMarginsOf`, GraphGeometry.kt:161), поэтому «вся история» на полосе шире реальной на
   ~2 % и на 0.4× сжимается вместе с содержимым. Заметить это глазом нельзя; записано, чтобы не
   искать потом расхождение в один процент.
9. **Полоса занимает 48 dp низа экрана всегда**, в том числе когда содержимое видно целиком и
   рамка равна треку. Это решение брифа (§18, п. 5), а не недосмотр.

## 6. Минимальная перестройка

1. **`GraphCanvas`: зоны становятся множественными и живут в координатах корня.** Причина — §3.1 и
   §3.2: одна зона не вмещает двух инструментов, а `boundsInParent()` врёт, как только инструмент
   перестаёт быть прямым ребёнком полотна.
2. **`GraphDebugOverlay`: отдаёт `boundsInRoot()` и свой ключ, снимает зону по ключу.** Причина —
   следствие пункта 1; без этого панель перестанет блокировать жест.
3. **`GraphCanvasState`: три новых `State` и `scrubTo`.** Причина — `placement` наружу не отдаётся,
   и перевод «камера → доля» может жить только здесь (§2.3).
4. **Новый `GraphMinimapGeometry.kt` с четырьмя чистыми функциями.** Причина — канон «чистая
   функция раньше класса»: всё, что здесь может сломаться, обязано проверяться на JVM.
5. **Новые сущности `GraphViewportSpan` и `GraphLaneMark` в `ui/entity`.** Причина — правило «один
   класс — один файл».
6. **Новый маппер `Int.toLaneColor()` в `ui/mapper/GraphLaneMappers.kt`.** Причина — цвет
   идентичности нужен уже трём потребителям; сейчас он живёт приватной копией в превью
   `GlyphNode.kt`.
7. **Новый компонент `GraphMinimap` с парой превью Light/Dark через `@PreviewParameter`.** Причина —
   конвенция проекта на превью.
8. **`ChronologyScreen`: панель и мини-карта — в общей `Column` у нижнего края, мини-карта внизу.**
   Причина — §11.1: появление панели не должно двигать мини-карту, а `Column`, растущая вверх от
   нижнего края, это и обеспечивает.
9. **`nearestCentreIndexOf` в `GraphGeometry.kt`.** Причина — вопрос о раскладке решается там, где
   живёт раскладка.

Пункты 1, 2, 8 — перестройка существующего; 3 — дополнение; 4–7, 9 — новый код.

## 7. Тесты, которые надо написать

**`GraphMinimapGeometryTest`** — KDoc класса: «Перевод камеры в долю полосы и обратно вынесен в
чистые функции затем, чтобы проверять его без Compose и без устройства. Сторожит: вырожденная
история не должна давать деления на ноль, расширенная под палец рамка не должна уводить камеру, а
обратный перевод обязан попадать в ту же долю, из которой взят».

Прямое преобразование:

- `` `the frame spans the whole track when the history fits the screen` ``
- `` `the frame narrows in proportion to the zoom` ``
- `` `the frame stays inside the track at either end` ``
- `` `an empty history keeps the frame still instead of dividing by zero` ``
- `` `a single node history keeps the frame across the whole track` ``

Минимальная ширина:

- `` `a frame thinner than a fingertip is widened around its own centre` ``
- `` `widening never pushes the frame off the track` ``

Обратное преобразование:

- `` `scrubbing to the middle brings the middle of the history to the centre of the screen` ``
- `` `scrubbing past the end is clamped to the camera range` ``
- `` `the scrubbed camera returns the same fraction it was asked for` `` — сторож согласованности
  прямого и обратного преобразований; ломается, если политику `cameraRangeOf` поменяют, не заглянув
  сюда
- `` `scrubbing an empty history moves nothing` ``

Засечки и ближайший узел:

- `` `a lane mark stands where the first node of its lane stands` ``
- `` `the trunk has no lane mark of its own` ``
- `` `lane marks survive a graph whose nodes are not sorted by lane` ``
- `` `the nearest node is chosen by distance, not by order in the list` `` (в `GraphGeometryTest`)

**`GraphCanvasStateTest`** — дополняется одним: `` `a scrub stops the fling it interrupts` ``.

Итого 16 новых тестов к нынешним 83.

## 8. Что проверять на устройстве

У агента устройства нет — это раздел документа, а не оговорка.

1. **Хват рамки на 2.5×**: честные 9.4 dp показаны как 32. Ловится ли пальцем и не выглядит ли
   рамка обманом на фоне того, что видно на экране.
2. **Насыщение на 0.4×**: докрутив к началу истории, рамка встаёт у края полосы и дальше не идёт,
   пока камера ещё едет. 20 dp хода вхолостую — читается это как упор или как залипание.
3. **Скраб под навигационной полосой**: полоса стоит над `navigationBarsPadding()`, но жест «домой»
   у нижней кромки может перехватываться системой раньше.
4. **Зоны жеста**: палец на панели и палец на мини-карте не двигают граф; палец на графе между ними
   двигает. Отладочная панель показывает `pan = 0` в первых двух случаях.
5. **Скраб во время инерции**: бросок обязан обрываться в момент касания полосы, а не бороться со
   скрабом.
6. **Пинч и скраб одновременно** — два разных `pointerInput`: палец на полосе, два пальца на графе.
   Поведение не проектировалось; проверить, что не приводит к рывку камеры.
7. **Пузырь даты** не выезжает за края экрана у самых краёв полосы и не мигает при быстром скрабе.
8. **Поворот экрана**: `viewport` меняется, рамка обязана пересчитаться (камера при этом
   сбрасывается — `rememberSaveable` отложен журналом отдельно).
9. **Обе темы**: засечки `graphLane*` на `cardPrimary` в тёмной и светлой; акцентная рамка на
   тёмной — контраст акцента там 2.5 : 1, для заливки это законно, но выглядеть должно.
10. **Крупный системный шрифт**: пузырь даты на 200 % не должен ломать полосу.

## 9. Что осталось непроверенным

1. **Ширина экрана 412 dp — допущение.** Вся таблица §2.2 масштабируется линейно, но порог
   0.738×, за которым рамка становится минимальной, зависит от ширины экрана: на планшете он
   сдвинется вниз, и честная пропорция будет держаться дольше.
2. **Плотность засечек на реальной переписке.** 13 засечек демо-набора на 372 dp — по 28 dp на
   штрих. На переписке с 40 ветками они сольются в гребёнку. Порога «слишком много засечек» проект
   не вводит: до реальных данных это спекуляция, а на демо-наборе проблема не воспроизводится.
3. **Одновременный пинч и скраб** — поведение не спроектировано, только вынесено в проверку (§8.6).
   Если рывок обнаружится, дешёвый обратный ход — не начинать жест полотна, пока идёт скраб.
4. **Совместимость с будущей виртуализацией.** `bounds` берётся из раскладки скомпонованных узлов;
   когда компоноваться будет только видимое, мир мини-карты поедет вместе с камерой. Журнал уже
   держит это как отложенное для камеры — мини-карта добавляет к нему второго потребителя.
5. **Как мини-карта уживётся с уровнями детализации.** LOD 1 меняет раскладку (глифы вместо плашек,
   сжатые зазоры), то есть `bounds` изменится скачком, и мир мини-карты изменится вместе с ним.
   Проверить это негде, пока LOD не сделан.
