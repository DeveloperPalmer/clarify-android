Хранилище чата: от SQLDelight к Room, урок за уроком

План переписывает локальную базу с SQLDelight на Room в том порядке, в каком это удобно учить: от одной таблицы из двух столбцов до шести таблиц чата с join-ами, внешними ключами и транзакциями. У каждого урока записано, что делаем, зачем, куда это ложится и почему именно так. Решены вопросы 01–07, 09–12 и 18–21, открыты 08 и 13–17: у каждого есть рекомендация и пункт, который он блокирует.

Формат: учебный план + трекер Объём: 2 базы, 7 таблиц, 45 запросов, 5 репозиториев Библиотека: Room 3.0.3 Обновлено: 09.10.2026

Где мы и куда идём

Сейчас в модуле database живут две базы SQLDelight. PersistedDB — одна таблица Settings (токены сессии, курсор событий), файл clarify.db переживает перезапуск. InMemoryDB — шесть таблиц кэша чата, создаётся с name = null и умирает вместе с процессом. Обе используются через сгенерированные *Queries: около ста обращений в пяти репозиториях, двадцать транзакций. Тестов на запросы нет — только на адаптер CommitReplyAdapter.

Словарь: что чему соответствует

Всё, что в SQLDelight делал .sq-файл, в Room раскладывается по аннотациям и классам. Правая колонка — главное: места, где это не просто переименование.

SQLDelightRoomЧто меняется по сути
CREATE TABLE в .sq @Entity + @PrimaryKey, indices, foreignKeys Схема пишется на Kotlin; SQL из неё Room генерирует сам и экспортирует в JSON.
именованный запрос в .sq метод DAO с @Query SQL остаётся строкой в аннотации; KSP проверяет его при сборке по схеме.
ColumnAdapter и AS Тип @ColumnTypeConverter, подключённый на базе через @ColumnTypeConverters Тип колонки больше не виден в схеме — он выводится из типа поля сущности. В Room 3 аннотации переименованы: @TypeConverter → @ColumnTypeConverter, @TypeConverters → @ColumnTypeConverters, @ProvidedTypeConverter → @ProvidedColumnTypeConverter. value class конвертера не требует.
Query<T>.asFlow().mapToList() метод DAO, возвращающий DistinctFlow<List<T>> Тот же принцип: перевыпуск на любую запись в таблицы запроса, включая таблицы подзапросов. Встроенный Flow Room дедупликацию из Flows.kt теряет; её возвращает свой тип через @DaoReturnTypeConverter — механизм Room 3 (вопрос 11).
executeAsOneOrNull() в withContext(IO) suspend-метод DAO Room сам уходит с главного потока; обёртка withContext(Dispatchers.IO) перестаёт быть нужной.
лямбда-маппер select(id, ::mapToUser) класс-проекция строки + toDomainModel() Столбцы перестают передаваться по позициям; на каждый JOIN появляется свой класс (вопрос 10).
database.transaction { } database.withWriteTransaction { } Лямбда становится suspend: внутри можно вызывать suspend-DAO (вопрос 14). В Room 3 withTransaction на базе нет: есть withWriteTransaction и withReadTransaction — найдено в артефакте room3-runtime 3.0.3; поведение проверит 8.1.
INSERT OR REPLACE @Upsert или @Query с ON CONFLICT REPLACE — это «удалить и вставить»; при включённых внешних ключах он каскадом сносит дочерние строки (вопросы 12, 13).
внешние ключи: в драйвере выключены включаются при открытии базы (ожидание, проверяется в 7.4) Молчаливый ON DELETE CASCADE, которого не было, вдруг работает, а вставка сироты начинает падать.
AndroidSqliteDriver(name = null) Room.inMemoryDatabaseBuilder<T>() + setDriver(AndroidSQLiteDriver()) База по-прежнему умирает вместе с процессом; закрывать её нельзя.

Код первого урока

Слева — всё, что сейчас описывает Settings в SQLDelight. Справа — то же тремя аннотациями. Это наброски: они не компилировались.

сейчастаблица и запросы в одном файлеSettings.sq
CREATE TABLE Settings (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL
);

selectByKey:
SELECT value FROM Settings WHERE key = ? LIMIT 1;

insertOrReplace:
INSERT OR REPLACE INTO Settings VALUES (:key, :value);

deleteByKey:
DELETE FROM Settings WHERE key = ?;
Схема и запросы рядом; типы Kotlin рождаются кодогенерацией, потребитель ходит в settingsQueries.
набросоктри роли — три файлаentity/ · dao/ · SettingsDatabase.kt
@Entity(tableName = "Settings")
data class SettingsEntity(
  @PrimaryKey val key: Key,
  val value: String
) {
  @JvmInline
  value class Key(val key: String)
}

@Dao
interface SettingsDao {
  @Query("SELECT value FROM Settings WHERE key = :key LIMIT 1")
  suspend fun select(key: SettingsEntity.Key): String?

  @Query("SELECT value FROM Settings WHERE key = :key LIMIT 1")
  fun observe(key: SettingsEntity.Key): Flow<String?>

  @Insert(onConflict = OnConflictStrategy.REPLACE)
  suspend fun insertOrReplace(entity: SettingsEntity)

  @Delete(SettingsEntity::class)
  suspend fun delete(key: SettingsEntity.Key)
}

@Database(entities = [SettingsEntity::class], version = 1, exportSchema = true)
abstract class SettingsDatabase : RoomDatabase() {
  abstract fun settingsDao(): SettingsDao
}
Сущность — это строка, DAO — набор запросов, база — точка входа. Реализацию DAO и базы пишет KSP.

Как читать этот код: ваше понимание и уточнения

Средняя колонка — как понято с первого прочтения, правая — что к этому стоит добавить. Метки: верно понято правильно, уточнено верно по сути, но есть деталь, дополнено было непонятно, объяснение добавлено.

ЧастьКак понятоУточнение
@Databaseуточнено Абстрактный класс, в котором описаны DAO. Класс наследует RoomDatabase, а каждый DAO отдаётся абстрактным методом: abstract fun settingsDao(): SettingsDao. Тело классу не нужно — реализацию SettingsDatabase_Impl пишет KSP при сборке. Поэтому базу нельзя создать через конструктор: её собирает билдер.
entitiesверно Массив таблиц, каждая описана data-классом. Таблица появляется только у того класса, что перечислен в entities и помечен @Entity. Имя таблицы — tableName, первичный ключ — @PrimaryKey, тип столбца Room выводит из типа поля (String → TEXT). Для ChatDatabase в списке будет шесть сущностей.
versionуточнено Версию поднимаем при миграции. Поднимаем при любом изменении схемы: новая таблица, столбец, индекс. Миграция — это отдельная инструкция, как перенести данные со старой версии на новую. Room хранит в служебной таблице room_master_table хэш схемы (identity_hash, он виден в 1.json) и сверяет его с кодом при открытии. Схема изменилась, версия нет — база не откроется с ошибкой о целостности. У нас данные тестовые и миграции не пишем, но версию всё равно поднимаем.
exportSchemaдополнено Не понял, что делает. При сборке Room записывает описание схемы в JSON: таблицы, столбцы, ключи, индексы, хэш. Файл лежит там, куда указывает schemaDirectory, — у нас database/schemas/<класс базы>/<версия>.json, по файлу на каждую версию. Зачем он: 1) схема попадает в git, и изменение таблицы видно в ревью как обычный дифф; 2) это эталон для миграций — тест миграции берёт JSON старой версии и проверяет, что после неё база совпала со схемой новой; 3) автомиграции строятся как разница двух JSON. Без schemaDirectory Room при exportSchema = true предупредит об этом — плагин androidx.room3 в build.gradle как раз его и задаёт. Откройте 1.json и найдите createSql: это SQL, который Room выполнит при создании базы.
@Daoуточнено Интерфейс, описывающий запросы к базе в формате SQL; проверяется на этапе компиляции. SQL нужен не всегда: @Insert, @Update, @Delete, @Upsert генерируют запрос сами, свой SQL пишется в @Query. Компиляция проверяет, что таблицы и столбцы из запроса есть в сущностях, а типы параметров и результата подходят. @Delete принимает объект сущности, список объектов или частичный класс только с полями первичного ключа — тогда пишется @Delete(SettingsEntity::class), а поле класса называется как столбец. Опечатка в имени столбца ломает сборку. Смысл запроса она не проверяет: перепутанное условие WHERE соберётся — для этого и нужны тесты из Урока 2. Тип результата задаёт поведение: suspend — разовый вызов в фоне, Flow — подписка, которая получает новое значение после любой записи в таблицу.
Создание базыуточнено Подключаем через Room.buildDatabase; можно ещё подключить базу в памяти через InMemory. Метод называется Room.databaseBuilder(context, SettingsDatabase::class.java, "settings.db"), а в Room 3 перед .build() обязательно добавляется .setDriver(AndroidSQLiteDriver()). Он создаёт файл на диске, данные переживают перезапуск процесса. Для памяти — Room.inMemoryDatabaseBuilder<ChatDatabase>() тоже с драйвером: имени файла нет, база умирает вместе с процессом, как сегодняшняя InMemoryDB с name = null. Это разные билдеры, а не режим одной базы. Экземпляр дорогой (внутри пул соединений), поэтому в DI он один на процесс.

Как всё связано: @Database владеет списком @Entity и отдаёт @Dao; DAO обращаются к таблицам этих сущностей; билдер превращает описание в живой объект. Три аннотации — три роли: что хранится, как спрашивать, где живёт.

Курс по урокам: что, зачем, куда, почему

Тот же рассказ повторяется при сдаче каждого этапа, только с реальным диффом. Здесь — заранее, чтобы видеть весь маршрут.

Урок 1 · Первая таблица: Settings в Room

Что
Подключаем Room и описываем первую таблицу тремя аннотациями: @Entity — строка, @Dao — запросы, @Database — точка входа. Базу сразу заводим в DI.
Зачем
Settings — два текстовых столбца. На ней виден весь контур Room без побочных эффектов: ни join-ов, ни ключей, ни конвертеров.
Куда
Модуль database: entity/SettingsEntity.kt, dao/SettingsDao.kt, SettingsDatabase.kt; провайдер — в di/DatabaseModule.kt. Версии — в gradle/libs.versions.toml.
Почему так
Room — аннотационный процессор: KSP читает аннотации и пишет реализацию на этапе сборки, поэтому опечатка в SQL ломает компиляцию, а не рантайм. Плагин androidx.room3 кладёт JSON схемы в schemas/ — эталон для будущих миграций.

Урок 2 · Как проверять DAO

Что
Тест SettingsDao на in-memory базе в обычном JVM-тесте, без эмулятора.
Зачем
С SQLDelight запросы не проверялись вовсе. Дальше переписывается сорок пять запросов; тест превращает «кажется, то же самое» в факт.
Куда
database/src/test, JUnit 5 — как уже стоит в проекте.
Почему так
Память SQLite принадлежит соединению: если Room откроет несколько, запись и подписка увидят разные базы. Поэтому в тесте обязателен случай «записали — Flow получил». Урок спайковый: если путь не работает, он отдаётся на ревью и откатывается.

Урок 3 · Подключаем Settings

Что
Два потребителя (AuthSessionPersistenceImpl, PersistedEventCursorStore) переходят на SettingsDao; Settings.sq и PersistedDB исчезают.
Зачем
Первый полный круг «старое → новое» на маленьком кусочке. Проблемы с файлом БД и токенами всплывут здесь, а не посреди чата.
Куда
DatabaseModule, два класса в auth-session и app/data, блок sqldelight {} в database/build.gradle.
Почему так
Токены — единственное, что переживает перезапуск; сломать их значит разлогинить, поэтому проверяем руками. Suspend-методы Room сами уходят с главного потока — withContext(Dispatchers.IO) вокруг них убираем.

Урок 4 · Схема чата

Что
Учим Room типам-обёрткам через конвертеры, описываем шесть таблиц сущностями с индексами и внешними ключами, собираем ChatDatabase без запросов.
Зачем
Схема — фундамент запросов. Экспортированный JSON можно положить рядом с CREATE TABLE из .sq и убедиться, что ничего не потеряно.
Куда
converter/, entity/, ChatDatabase.kt в модуле database.
Почему так
В SQLDelight тип колонки задавало слово AS в .sq, в Room — функция-конвертер на базе. Составной ключ ChatMember и индексы переносим дословно: порядок колонок ключа — это индекс, а не косметика.

Урок 5 · Чтение I: пользователи, участники, разговоры

Что
Все виды SELECT, что есть в проекте: простые, JOIN, подзапрос COUNT, GROUP BY … HAVING, IN-список.
Зачем
После этого урока остальные таблицы проходятся по аналогии: каждый приём уже встречался.
Куда
dao/UserDao, ChatMemberDao, ChatConversationDao; классы-проекции — в entity/.
Почему так
SQLDelight отдавал столбцы в лямбду, Room возвращает класс, поэтому на каждый JOIN появляется проекция. Наблюдаемый запрос по-прежнему перевыпускает значение на любую запись в таблицу — отсюда вопрос о дедупликации.

Урок 6 · Чтение II: ветки и коммиты

Что
Ветки с LEFT JOIN на запрос слияния; коммиты с курсорами, фильтром createdAtNanos > 0 и IN-списком.
Зачем
Самые горячие таблицы: на них держатся ленты сообщений и граф хронологии.
Куда
dao/ChatBranchDao, dao/ChatCommitDao. У MergeRequest своих чтений нет — он читается только через ветку.
Почему так
Nullable-столбцы LEFT JOIN — место, где теряется инвариант «запрос слияния есть целиком или нет вовсе». Тест фиксирует его до того, как на нём построят маппер.

Урок 7 · Запись

Что
Вставки, изменения, удаления и семантика INSERT OR REPLACE при включённых внешних ключах.
Зачем
REPLACE — «удалить и вставить». Пока ключи выключены, это незаметно; Room их включает, и REPLACE разговора каскадом снесёт его ветки и коммиты.
Куда
Методы записи в тех же DAO, тесты каскадов и ключей рядом с ними.
Почему так
Самый поучительный урок: одна и та же строка SQL ведёт себя по-разному в зависимости от настройки соединения. unreadCount сегодня хранит COALESCE — это поведение надо сохранить.

Урок 8 · Подключаем чат

Что
Провайдер ChatDatabase, очистка сессии и пять репозиториев переходят на DAO вместе с мапперами.
Зачем

Как сохранить гарантию «наблюдаемый запрос всегда дедуплицирован»?
Сегодня Flows.kt — единственная точка, возвращающая Flow; сырого потока нет в API по типу. DAO Room вернёт Flow напрямую, и гарантия превращается в дисциплину. Рекомендация: DAO возвращают Flow, репозитории вешают distinctUntilChanged(); причина (потерянный дневной лимит Firestore, SnapshotIdSet) переезжает в KDoc DAO и в будущее правило по Room. Альтернатива: оставить обёртки-расширения над DAO — тип снова защищает, но появляется второй слой. Решено иначе: DAO отдают свой тип DistinctFlow<T>. Его конструктор закрыт и всегда добавляет distinctUntilChanged(); строит его единственный @DaoReturnTypeConverter — DistinctFlowConverter, подключённый на ChatDatabase. DAO остаются интерфейсами, гарантия видна в сигнатуре каждого запроса, причина — в KDoc DistinctFlow. Промежуточный вариант — абстрактный DAO с protected сырым методом и публичной обёрткой — работал, но удваивал каждую декларацию и отвергнут вами. Остаётся дыра: Flow<T> в DAO никто не запрещает — её закрывает ревью и правило блока 10. Тест на чувствительность: без distinctUntilChanged() в DistinctFlow тест повторов падает. Меняет 5.1.
