# Камера полотна: инерция по 360°

Наработки под требование владельца: «Скролл работает, но нет fling. Только топорное движение пальца,
а движение должно работать как будто бы я чат скролю, а не просто двигаю холст. Движение возможно по
двум осям и по диагонали соответственно, и fling должен работать на 360».

Документ самодостаточен: он рассчитан на сессию, которая берёт задачу с нуля. Ничего не реализовано —
это разведка, спецификация и рекомендация. Журнал фичи — [chronology-log.md](chronology-log.md),
дизайн-бриф — [chronology-design-prompt.md](chronology-design-prompt.md).

**Статус:** разведка закончена и проверена по исходникам на диске. Фаза проектирования (три
независимых подхода, судейство по трём линзам, синтез) **не доиграла** — прогон умер на лимите
сессии, потом процесс завершился. Раздел «Рекомендация» ниже — мой вывод из разведки, а не результат
судейства.

## Что означает «как в чате» — численно

Список, ощущение которого просят повторить, лежит в `uikit/.../component/chat/ChatCommits.kt:139` и
это **обычный `LazyColumn` с дефолтным `FlingBehavior`**, ничего не настроено. Значит требование
переводится однозначно: нужен `ScrollableDefaults.flingBehavior()`, то есть
`rememberSplineBasedDecay<Float>()`. Не «что-нибудь затухающее», а именно эта кривая.

Цепочка проверена по исходникам: `ScrollableDefaults.flingBehavior()` →
`rememberPlatformDefaultFlingBehavior()` → `DefaultFlingBehavior(rememberSplineBasedDecay<Float>())`
(`Scrollable.android.kt:29`). Спека — `androidx.compose.animation.SplineBasedFloatDecayAnimationSpec`,
порт `android.widget.Scroller`: кубический безье с натяжениями 0.5/1.0, точкой перегиба 0.35 и
таблицей на 101 точку.

Константы дословно из `FlingCalculator.kt` / `SplineBasedDecay.kt`:

```kotlin
private const val GravityEarth = 9.80665f
private const val InchesPerMeter = 39.37f
private val DecelerationRate = (ln(0.78) / ln(0.9)).toFloat()   // 2.3582018
private fun computeDeceleration(density: Density) =
    GravityEarth * InchesPerMeter * density.density * 160f * 0.84f
private const val Inflection = 0.35f
```

Закрытая форма, выведенная из `flingInfo` и проверенная численно:

```
fc       = friction * 9.80665 * 39.37 * density * 160 * 0.84      // friction = ViewConfiguration.getScrollFriction()
distance = fc^(1-n) * (0.35 * |v|)^n ,  n = D/(D-1) = 1.7362676
duration = 1000 * (0.35 * |v| / fc)^m ,  m = 1/(D-1) = 0.7362676
```

**Спека, к которой приводится дизайн.** Плотность входит так, что физический результат от неё не
зависит: `distance` в dp и `duration` в мс — инварианты. Проверено на density 1.0 / 2.0 / 2.75 / 3.5.

| Скорость отпускания | Пролёт | Длительность |
|---|---|---|
| 300 dp/s | 24 dp | 229 мс |
| 1000 dp/s | 194 dp | 555 мс |
| 2000 dp/s | 647 dp | 925 мс |
| 3000 dp/s | 1309 dp | 1247 мс |
| 5000 dp/s | 3178 dp | 1816 мс |
| 8000 dp/s | 7186 dp | 2567 мс |

### `exponentialDecay` под платформу не подгоняется

Это не вкусовщина, а разные показатели степени: у spline `distance ∝ v^1.736`, у
`exponentialDecay` — строго `∝ v`.

| | spline (платформа) | `exponentialDecay(1f)` |
|---|---|---|
| удвоить скорость броска | пролёт ×3.33, время ×1.67 | пролёт ×2, время **+165 мс** и всё |
| `absVelocityThreshold` | 0 — доигрывает до конца | 0.1 px/s, обрезается |
| конец | конечная длительность, скорость ровно 0 | асимптота |

На density 2.75: при 1000 px/s spline даёт 92 px за 264 мс, экспонента — 238 px за 2193 мс. Подогнав
`frictionMultiplier` под быстрый флик, на медленном промахнёшься в 2.6 раза. Ощущение экспоненты —
«ватное, длинное, не приземляется».

## Почему инерции нет сегодня

`GraphCanvas.kt:69` использует `detectDragGestures`, а **обе его перегрузки в foundation отдают
`onDragEnd` без параметров** — скорости не дают ни в каком виде. То есть дело не в неправильном
затухании: начальная скорость нигде не измеряется. Это единственный жест во всём приложении, и
`VelocityTracker`, `splineBasedDecay`, `animateDecay`, `FlingBehavior`, `scrollable`, `draggable`,
`overscroll`, `nestedScroll` в репозитории не встречаются ни разу.

## Дефект камеры, который придётся починить первым

Инерцию нельзя добавить, не тронув камеру: сейчас сдвиг накапливается без границ, а кламп стоит
только на чтении.

```kotlin
// GraphCanvasState.kt:128-129 — записи без клампа и без знания диапазона
rawOffsetX += delta.x
rawOffsetY += delta.y

// GraphCanvasState.kt:94-95 — единственный кламп, на чтении
x = if (isMoved) rawOffsetX.coerceIn(rangeX) else rangeX.endInclusive
```

Записей ровно три: инициализация (`:61-62`), засев в `pan()` (`:123-124`), накопление (`:128-129`).
Обратной записи нет нигде; ни `layout()`, ни `setNodes()` их не трогают.

**Трассировка на числах существующего теста** (viewport 1000, `centreSpanX = 60f..900f`, значит
`rangeX = -400f..440f`):

1. Покой: `isMoved == false`, показывается `440`.
2. Первый `pan` засевает `rawOffsetX = 440`.
3. Тянем влево на 3840: `rawOffsetX = -3400`, показывается `-400`. Картинка **верная**.
4. Забанковано перерегулирование: 3000 px.
5. Тянем обратно на 100: `rawOffsetX = -3300`, показывается `-400`. **Ни один пиксель не двинулся.**

Три следствия, каждое хуже предыдущего:

**Мёртвая зона накапливается за жизнь экрана.** Ничто не сбрасывает `rawOffset`, поэтому каждый упор
в стенку добавляет к ней, и сама она не уменьшается.

**По вертикали она копится всегда.** При одной дорожке содержимое ниже вьюпорта, `panRangeOf`
(`GraphGeometry.kt:180-181`) возвращает вырожденный центрирующий диапазон — и *весь* вертикальный ход
каждого свайпа уходит в `rawOffsetY` безвозвратно. Любой слегка наклонный свайп банкует Y.

**Проявляется это телепортом, а не залипанием.** Пришло сообщение → `setNodes` → `layout()` →
`centreSpanX` вырос → `rangeX.start` опустился → камера за кадр уезжает на величину банка. Выглядит
как криво сделанное авто-следование, которое потом загадочно прекращается. Вертикальный вариант
резче: пока содержимое влезает по высоте, `rangeY` вырожден и копит; как только граф получит дорожку
и станет выше вьюпорта, `offset.y` прыгнет с центрирующего значения прямо на зажатый банк.

Отдельно: `isMoved` защёлкивается навсегда (`:126`, сброса нет), поэтому правило покоя «первый узел в
центре» после первого касания не применяется больше никогда, и новые узлы не перецентрируются. Флаг
смешивает два смысла — «пользователь взял управление» и «`rawOffset` засеян», — а для инерции нужен
третий: «камерой управляет анимация».

Проверено попутно: пустой диапазон невозможен ни у `timelinePanRangeOf`, ни у `panRangeOf`, поэтому
`coerceIn` на записи не бросит.

### Что сделает затухание, если этого не починить

`pan()` возвращает `Unit`, то есть у анимации нет ни одного признака, что дельта отвергнута.
Платформенный fling гасится ровно сравнением запрошенного с потреблённым
(`DefaultFlingBehavior.performFling`: `if (abs(delta - consumed) > 0.5f) this.cancelAnimation()`).
Этого сигнала здесь физически нет, поэтому затухание доработает свою длительность целиком, кормя
`pan()` за границей: **один резкий флик забанкует несколько тысяч пикселей мёртвой зоны там, где
палец банковал сотни.**

**Отладочная панель этого не покажет — и это надо починить вместе.** Строка `pan` будет тикать с
частотой кадров, но не покраснеет: `FRAME_LIMIT = 140` (`GraphTelemetryMappers.kt:59`) выше 120 Гц. А
`layer` покажет ≈0/s, потому что пересчёт `offset` даёт структурно равный `Offset` и читателя в
`graphicsLayer` не инвалидирует. По той же причине встанут `edges`, `backdrop`, `overlay` и строка
`camera`. Отпечаток «анимация молотит в стенку» — это `pan ≈ fps` при `layer ≈ 0`, и сейчас панель
его не различает. Плюс `lastPan` перетирается дельтами затухания, так что строка `last pan` после
каждого флика вырождается в «0, 0».

## Ловушка: покомпонентное затухание гнёт диагональ

Первое, что приходит в голову — `Animatable<Offset, AnimationVector2D>.animateDecay(splineBasedDecay())`.
Это неверно, и вопрос даже не «одна 2D-анимация или две 1D»: **это одно и то же.**
`FloatDecayAnimationSpec.generateDecayAnimationSpec<T>()` даёт `VectorizedFloatDecaySpec`, который
применяет float-спеку к каждой оси отдельно и берёт `maxOf` по длительностям. KDoc не оставляет
трактовок: *«by applying the given `FloatDecayAnimationSpec` on every dimension»*.

Прямая траектория получается ⟺ путь по оси линеен по начальной скорости. У экспоненты
`s(v,t) = v·(e^{ft}-1)/f` — множитель выносится, **покомпонентная экспонента прямую не гнёт**
(проверено численно: бросок 30°, `y/x = 0.577350269` на всём интервале, ровно `tan 30°`). У spline
`n = 1.736 ≠ 1` и `m = 0.736 ≠ 0`, и ломаются оба условия.

**Конечная точка уходит с направления броска**: `θ_end = atan((tan θ)^1.7362676)`. Плотность сюда не
входит, искажение чисто геометрическое.

| Бросок | Прилёт | Увод |
|---|---|---|
| 10° | 2.81° | 7.19° |
| **22.15°** | 11.86° | **10.29° — максимум** |
| 30° | 21.07° | 8.93° |
| 45° | 45.00° | 0° |
| 60° | 68.93° | −8.93° |

Инвариантны только 0°, 45° и 90°; всё остальное присасывается к ближней оси.

**И траектория выгибается, а в конце ломается в крючок**, потому что длительности осей разные
(`Ty/Tx = (tan θ)^0.736`): после `min(Tx, Ty)` одна ось стоит, а вторая ещё едет.

| Бросок | Доля fling'а по одной оси | Макс. отклонение от хорды |
|---|---|---|
| 10° | 72.1 % | — |
| 15° | — | 22.7 px (3.9 %) |
| 30° | 33.3 % | **28.8 px (5.6 %)** |
| 45° | 0 % | 0 |

На полотне это читается как «дёрнул по диагонали, а оно доехало горизонтально».

## Как это решает сама платформа

В foundation есть `Modifier.scrollable2D` со `Scrollable2DState`, и он **покомпонентно не затухает**.
`ScrollingLogic2D.doFlingAnimation` сводит скорость к модулю, гоняет через **одномерный**
`FlingBehavior` и раскладывает скалярную дельту по **зафиксированному на отпускании** углу:

```kotlin
fun Offset.toMagnitudeFloat() = sqrt(x.pow(2) + y.pow(2))
fun Float.toDecomposedOffset() =
    if (available.angle.isNaN()) Offset(0f, this)
    else Offset(x = abs(cos(available.angle) * this) * sign(available.x),
                y = abs(sin(available.angle) * this) * sign(available.y))
// …
private val Velocity.magnitude get() = sqrt(x.pow(2) + y.pow(2))
private val Velocity.angle     get() = atan2(x = x, y = y)
```

Отсюда: траектория строго прямая по направлению отпускания для всех 360°; пролёт и длительность равны
одномерным, то есть таблице выше без поправок на угол; спецкейсов нет, кроме защиты
`angle.isNaN()`. Работает это ещё и потому, что `magnitude ≥ 0`, значит скалярная анимация монотонно
растёт от нуля и сравнение `abs(delta - consumed) > 0.5f` корректно — знаки живут только в `sign()`.

`Velocity.magnitude` и `Velocity.angle` **приватные**, так что руками их пришлось бы переписать.

**Проверяемое утверждение для юнит-теста:** для любого угла отпускания отношение накопленных
смещений `dy/dx` постоянно на всём интервале и равно `vy/vx`. Покомпонентная реализация этот тест
провалит, скалярная пройдёт.

### Опасность: foundation приходит транзитивно

**BOM в проекте нет, и `androidx.compose.foundation` не объявлен нигде** — ни в каталоге, ни в
бандле `android-ui`, ни в одном `build.gradle`. Версии прибиты руками: `compose = 1.11.4`,
`material3 = 1.4.0`. Разрешается при этом так:

```
androidx.compose.foundation:foundation-android:1.10.0   ← транзитивно через material3 1.4.0
androidx.compose.animation:animation-android:1.11.4
androidx.compose.ui:ui:1.11.4
```

То есть **foundation 1.10.0 при остальном 1.11.4**, и на 1.10.0 его держит только констрейнт
material3. Если инерция опирается на API foundation, стоит добавить в каталог
`compose-foundation = { module = "androidx.compose.foundation:foundation", version.ref = "compose" }`
и в бандл `android-ui`, чтобы foundation ехал вместе с остальным. Иначе поведение экрана зависит от
чужого графа зависимостей.

Путь «руками» (`VelocityTracker` + `splineBasedDecay` + `Animatable`) целиком лежит в
`animation`/`animation-core`/`ui` 1.11.4 — объявленных и версионированных верно.

## Рекомендация

Взять `Modifier.scrollable2D` с `flingBehavior = ScrollableDefaults.flingBehavior()`.

Основание: он даёт ровно ту кривую, которую просят (тот же `rememberSplineBasedDecay`, что у
`LazyColumn` в `ChatCommits.kt`), настоящую прямую по 360° через модуль и угол, трекинг скорости,
разведение пальца и анимации через `MutatorMutex`, nested scroll и опциональный overscroll — и всё
это стабильными API. Писать свою физику здесь значит переписать приватные `magnitude`/`angle` и
повторить таблицу пролётов, не получив ничего взамен.

Главное: **контракт `Scrollable2DState { delta -> consumed }` заставляет починить камеру.** Лямбда
обязана вернуть потреблённый `Offset`, и возврат меньшего — это и есть сигнал остановки у границы.
То есть кламп на записи и возврат потреблённого не «в довесок», а входной билет. Знак совпадает с
текущим `pan(dragAmount)` — содержимое идёт за пальцем, `reverseDirection` у `scrollable2D` нет.
`Scrollable2DState(...)` — не composable-фабрика, поэтому держатель может владеть им, и `GraphCanvas`
останется без арифметики.

Оговорка, из-за которой это рекомендация, а не решение: судейство не доиграло, и подход «руками»
разобран только с моей стороны. Его единственный настоящий плюс — он ближе к дом-стилю
`PredictiveBackController` и не трогает граф зависимостей.

### Минимальная перестройка

1. **Вынести диапазон камеры** из выражения внутри `offset` (`GraphCanvasState.kt:87-92`) в чистую
   функцию в `GraphGeometry.kt` от `(centreSpanX, bounds, viewport, isEmpty)`, отдающую оба диапазона
   одной сущностью в `entity/`. Одно определение «где камере можно быть» — и для чтения, и для
   записи, и юнит-тест без Compose.
2. **Вторая чистая функция**: по текущей камере, запрошенной дельте и диапазону вернуть новую камеру
   **и** потреблённую дельту. Это весь контракт инерции, выраженный арифметикой.
3. **`pan()` клампит на записи и возвращает потреблённое.** Правило «наружу только `State<T>`» это не
   нарушает: `pan()` исполняется в корутине жеста или анимации, а не в фазе Compose, поэтому чтение
   `placement`/`viewport` там ни на что не подписывает.
4. **`layout()` пере-зажимает сохранённую камеру** после обновления `viewport`/`placement` — тогда
   хранимое и показываемое не разъезжаются, и телепорты исчезают вместе с банком.
5. **Заменить блок `pointerInput`** на `Modifier.scrollable2D`. Приём `pointerInput(Unit)` +
   `rememberUpdatedState` уходит вместе с ним, но его задачу — не отменять жест при входящем
   сообщении — берёт на себя `Scrollable2DState`, живущий в держателе.
6. **Расщепить телеметрию `pan`** на жест и анимацию, добавить счётчик отвергнутой дельты и признак
   «идёт затухание». Иначе панель не отличит «идёт fling» от «fling молотит в стенку» от «крутится
   цикл», а это её единственное назначение.
7. **`isMoved` разложить** на «пользователь взял управление» и «камерой управляет анимация».

## Решения, которые надо принять явно

**Диагональ, упёршаяся одной осью.** `scrollable2D` сворачивает потреблённое в **модуль**
(`consumedOffset.toMagnitudeFloat()`), поэтому диагональный fling, у которого упёрлась только одна
ось, гасится целиком: бросок влево-вниз, доехавший до левого края при живом запасе снизу,
останавливается насмерть, а не съезжает вдоль края.

На этом экране это не краевой случай, а норма: при одной дорожке ось Y вырождена и не потребляет
ничего, значит естественный слегка наклонный флик может умирать мгновенно. Развилка — считать дельту
на оси без запаса **поглощённой** (инерция жива, идёт вдоль стенки, как в списке) или **отвергнутой**
(встаёт целиком, как у платформы). Требованию «360» отвечает первое: гасить, только когда обе оси не
потребили ничего. Это отход от платформы — значит решение с записанной причиной, а не побочный эффект
реализации. Место решения — чистая функция из пункта 2, там же и тест.

**Растяжение у края.** Стоит взять: `rememberOverscrollEffect()` + `Modifier.overscroll` + параметр
`scrollable2D`, двумерно из коробки, все четыре края и угол уже разобраны в
`AndroidEdgeEffectOverscrollEffect`. На полотне без скроллбара и без видимого конца это единственный
сигнал «дальше истории нет»; без него камера у границы просто перестаёт слушаться, и жест читается
как залипание.

**Токен затухания.** В `AppMotion` все токены — `tween`, ни одного decay или spring. При этом
`decelerate` (`AppMotion.kt:111`) заведён с KDoc «Без разгона… **Для камеры на полотне**», а
`largeTween()` — «перелёты камеры, стягивание линии». То есть дизайн-система про эту камеру уже
знает, а `DecayAnimationSpec<Float>` дома не имеет. Завести `flingDecay()` в `AppMotion` —
согласованный ход; по `.claude/rules/workflow.md` новый **токен** одобрения владельца не требует, в
отличие от нового правила.

## Дом-стиль, которому надо соответствовать

Образец держателя с корутинной анимацией — `core/routing/.../PredictiveBackController.kt`:
`@Stable` класс, анимируемые значения полями, снапшот-поля с `private set`, служебные счётчики
обычными полями, приём жеста — `suspend fun`, который только `snapTo`, а **финальная анимация
принимает scope параметром и не владеет им** (`:116-127`, `:140-145`). Причина в KDoc `:21-22`:
корутина жеста отменяется на отпускании, поэтому доигрывать надо в другой. Это ровно ситуация
инерции.

Соседа, которого нельзя задеть, зовут `PredictiveBackHandler` (`PredictiveNodeHost.kt:119`):
горизонтальный жест у левого края экрана съедает системный «назад», а не полотно. Значит нельзя
рассчитывать, что жест увидит все горизонтальные драги, и `change.consume()` (`GraphCanvas.kt:71`)
обязан остаться.

Тесты — JUnit 5, имена предложением в бэктиках. В бандле `unittest` **нет** ни compose-ui-test, ни
Robolectric, и `GraphCanvasStateTest` не существует. То есть арифметика инерции обязана быть чистой
функцией, чтобы вообще быть проверяемой.

## Тесты, которые надо написать

- `consumed delta equals the request while the camera has room`
- `consumed delta is truncated at the boundary`
- `consumed delta is zero on a saturated axis`
- `a degenerate range consumes nothing` — вырожденный диапазон это норма экрана, не краевой случай
- `a diagonal fling keeps its direction` — `dy/dx` постоянно и равно `vy/vx` на всём интервале
- `banked overshoot cannot outlive a layout pass` — сторож против телепорта при расширении диапазона

`GraphCanvasTelemetryTest` сломается на первом же новом счётчике: он строит `GraphTelemetry` девятью
позиционными аргументами. Это его назначение — он страж того, что счётчик проведён в `ratesOf`.

## Что проверять на устройстве

Эмулятора у агента нет, визуальную проверку делает владелец.

- Медленный флик не должен ощущаться как «палец отпустил, а оно не поехало»: своего порога скорости
  заводить не надо, платформенный барьер `abs(v) > 1f` — защита от `ln(0)`, а не UX-порог, и при
  137 dp/s spline пролетает 2.9 px за 61 мс, то есть кривая сама делает слабый флик невидимым.
- Диагональный бросок под 30° должен доезжать под 30°, а не под 21°.
- Флик по диагонали в угол — поведение сверить с принятым решением выше.
- В панели в покое: `pan` и `layer` по нулю. Во время затухания: `pan` и `layer` тикают **вместе**;
  `pan` при стоящем `layer` — это и есть «молотит в стенку».
- После упора в край жест обратно должен отвечать сразу, без мёртвой зоны.
- Проверить пролёт по таблице спеки: 1000 dp/s ≈ 194 dp за 555 мс. Забытый `Density` даёт ×2.106 и
  по пути, и по времени.

## Что осталось непроверенным

- **Фаза проектирования не доиграла.** Три подхода (`scrollable2D`, скалярное затухание руками,
  покомпонентное как foil), девять судейских проходов и синтез не выполнены. Прогон:
  `wf_367d6b45-820`, разведка в нём закэширована и возобновление отдаст её мгновенно.
- **Версия исходников.** Разрешается foundation **1.10.0**, а исходники читались в **1.10.6** (1.11.4
  в кэше нет). API совпадает, `Scrollable2DKt.class` есть в 1.9.4/1.9.5/1.10.0/1.10.6 и отсутствует в
  1.6.7. Но поведение на границе в этих версиях достигается **разными механизмами**: в 1.9.5 была
  развилка `isFlingContinuationAtBoundsEnabled` / `shouldCancelFling`, в 1.10.6 её убрали и оставили
  только `abs(delta - consumed) > 0.5f`. Что именно в 1.10.0 — не проверено.
- **`ViewConfiguration.getScrollFriction() == 0.015f`** — из AOSP по памяти, на диске не подтверждено:
  `android.jar` содержит только stubs.
- **`minimumFlingVelocity` в скролле Compose не применяется** — проверено grep'ом по foundation
  1.10.6: попадание только в `NestedScrollInteropConnection.android.kt`. Для 1.10.0 не перепроверено.
- **Одноосное гашение диагонали** выведено из чтения `doFlingAnimation` и структуры байткода —
  требует проверки на устройстве.
