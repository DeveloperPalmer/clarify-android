# Камера полотна: инерция по 360°

Наработки под требование владельца: «Скролл работает, но нет fling. Только топорное движение пальца,
а движение должно работать как будто бы я чат скролю, а не просто двигаю холст. Движение возможно по
двум осям и по диагонали соответственно, и fling должен работать на 360».

Документ самодостаточен: он рассчитан на сессию, которая берёт задачу с нуля. Ничего не реализовано —
это разведка, спецификация и рекомендация. Журнал фичи — [chronology-log.md](chronology-log.md),
дизайн-бриф — [chronology-design-prompt.md](chronology-design-prompt.md).

**Статус:** разведка закончена и проверена по исходникам на диске. Фаза проектирования **доиграла**:
три независимых подхода спроектированы, отсужены по трём линзам (физика, риск, конвенции) и сведены.
Раздел «Решение» ниже — результат судейства, и он **не совпал** с тем, что рекомендовала одна
разведка: победил не `scrollable2D`, а своя скалярная физика. Причина — в разделе «Ловушка, которой
не было в разведке».

Судейство переписало и часть самой разведки; исправления внесены по тексту, а спорные места помечены
на месте. Три проекта целиком и три вердикта судей лежат в
[chronology-camera-fling-design.md](chronology-camera-fling-design.md) — туда идти за основанием
вывода, сюда за самим выводом.

## Что означает «как в чате» — численно

Список, ощущение которого просят повторить, лежит в `uikit/.../component/chat/ChatCommits.kt:139` и
это **обычный `LazyColumn` с дефолтным `FlingBehavior`**, ничего не настроено. Значит требование
переводится однозначно: нужен `ScrollableDefaults.flingBehavior()`, то есть
`rememberSplineBasedDecay<Float>()`. Не «что-нибудь затухающее», а именно эта кривая.

Цепочка проверена по исходникам: `ScrollableDefaults.flingBehavior()` →
`rememberPlatformDefaultFlingBehavior()` → `DefaultFlingBehavior(rememberSplineBasedDecay<Float>())`
(`Scrollable.android.kt:29`). Спека — `androidx.compose.animation.SplineBasedFloatDecayAnimationSpec`,
порт `android.widget.Scroller`: кубический безье с натяжениями 0.5/1.0, точкой перегиба 0.35 и
таблицей на 101 точку.

Константы дословно из `FlingCalculator.kt` / `SplineBasedDecay.kt`:

```kotlin
private const val GravityEarth = 9.80665f
private const val InchesPerMeter = 39.37f
private val DecelerationRate = (ln(0.78) / ln(0.9)).toFloat()   // 2.3582018
private fun computeDeceleration(density: Density) =
    GravityEarth * InchesPerMeter * density.density * 160f * 0.84f
private const val Inflection = 0.35f
```

Закрытая форма, выведенная из `flingInfo` и проверенная численно:

```
fc       = friction * 9.80665 * 39.37 * density * 160 * 0.84      // friction = ViewConfiguration.getScrollFriction()
distance = fc^(1-n) * (0.35 * |v|)^n ,  n = D/(D-1) = 1.7362676
duration = 1000 * (0.35 * |v| / fc)^m ,  m = 1/(D-1) = 0.7362676
```

**Спека, к которой приводится дизайн.** Плотность входит так, что физический результат от неё не
зависит: `distance` в dp и `duration` в мс — инварианты. Проверено на density 1.0 / 2.0 / 2.75 / 3.5.

| Скорость отпускания | Пролёт | Длительность |
|---|---|---|
| 300 dp/s | 24 dp | 228 мс |
| 1000 dp/s | 194 dp | 555 мс |
| 2000 dp/s | 647 dp | 924 мс |
| 3000 dp/s | 1309 dp | 1246 мс |
| 5000 dp/s | 3178 dp | 1815 мс |
| 8000 dp/s | 7186 dp | 2566 мс |

Длительности перепроверены на судействе и уменьшены на 1 мс против первой редакции: `flingDuration`
делает `.toLong()`, то есть **усекает**, а не округляет (`FlingCalculator.kt:62`). Там же выяснилось,
что `getValueFromNanos` режет время до целых миллисекунд (`SplineBasedFloatDecayAnimationSpec.kt:47`)
— на пике 2000 dp/s это до 2 dp покадрового дрожания, одинаково при любом способе реализации.

### `exponentialDecay` под платформу не подгоняется

Это не вкусовщина, а разные показатели степени: у spline `distance ∝ v^1.736`, у
`exponentialDecay` — строго `∝ v`.

| | spline (платформа) | `exponentialDecay(1f)` |
|---|---|---|
| удвоить скорость броска | пролёт ×3.33, время ×1.67 | пролёт ×2, время **+165 мс** и всё |
| `absVelocityThreshold` | 0 — доигрывает до конца | 0.1 px/s, обрезается |
| конец | конечная длительность, скорость ровно 0 | асимптота |

На density 2.75: при 1000 px/s spline даёт 92 px за 264 мс, экспонента — 238 px за 2193 мс. Подогнав
`frictionMultiplier` под быстрый флик, на медленном промахнёшься в 2.6 раза. Ощущение экспоненты —
«ватное, длинное, не приземляется».

## Почему инерции нет сегодня

`GraphCanvas.kt:69` использует `detectDragGestures` в перегрузке, которая отдаёт `onDragEnd` без
параметров, и **скорость не измеряется нигде**. Дело не в неправильном затухании: измерять её просто
нечем. Это единственный жест во всём приложении, и `VelocityTracker`, `splineBasedDecay`,
`animateDecay`, `FlingBehavior`, `scrollable`, `draggable`, `overscroll`, `nestedScroll` в репозитории
не встречаются ни разу.

**Исправление первой редакции.** Здесь утверждалось, что `onDragEnd` без параметров у **обеих**
перегрузок и потому жест придётся переписывать на свой `awaitEachGesture`. Это неверно: перегрузка с
`orientationLock` объявляет `onDragEnd: (change: PointerInputChange) -> Unit` — up-событие, которого
достаточно, чтобы докормить `VelocityTracker` (`DragGestureDetector.kt:232-244`, публичная, `@OptIn`
use-site; есть и в 1.9.5, и в 1.10.0 байт в байт). Скорость она по-прежнему не считает, но своего
детектора жеста писать не надо — а это была главная статья расходов пути «руками».

Попутно: `change.consume()` в `GraphCanvas.kt:71` — **дубль**, foundation консьюмит сама
(`DragGestureDetector.kt:264`, `:308-312`). И держится он не на соседстве с `PredictiveBackHandler`:
тот `OnBackPressedCallback`, а не конкурент по pointer-событиям — краевой свайп система забирает до
Compose. Аргумент за `consume()` — только «жест не должен утечь в родителя».

## Дефект камеры, который придётся починить первым

Инерцию нельзя добавить, не тронув камеру: сейчас сдвиг накапливается без границ, а кламп стоит
только на чтении.

```kotlin
// GraphCanvasState.kt:128-129 — записи без клампа и без знания диапазона
rawOffsetX += delta.x
rawOffsetY += delta.y

// GraphCanvasState.kt:94-95 — единственный кламп, на чтении
x = if (isMoved) rawOffsetX.coerceIn(rangeX) else rangeX.endInclusive
```

Записей ровно три: инициализация (`:61-62`), засев в `pan()` (`:123-124`), накопление (`:128-129`).
Обратной записи нет нигде; ни `layout()`, ни `setNodes()` их не трогают.

**Трассировка на числах существующего теста** (viewport 1000, `centreSpanX = 60f..900f`, значит
`rangeX = -400f..440f`):

1. Покой: `isMoved == false`, показывается `440`.
2. Первый `pan` засевает `rawOffsetX = 440`.
3. Тянем влево на 3840: `rawOffsetX = -3400`, показывается `-400`. Картинка **верная**.
4. Забанковано перерегулирование: 3000 px.
5. Тянем обратно на 100: `rawOffsetX = -3300`, показывается `-400`. **Ни один пиксель не двинулся.**

Три следствия, каждое хуже предыдущего:

**Мёртвая зона накапливается за жизнь экрана.** Ничто не сбрасывает `rawOffset`, поэтому каждый упор
в стенку добавляет к ней, и сама она не уменьшается.

**По вертикали она копится всегда.** При одной дорожке содержимое ниже вьюпорта, `panRangeOf`
(`GraphGeometry.kt:180-181`) возвращает вырожденный центрирующий диапазон — и *весь* вертикальный ход
каждого свайпа уходит в `rawOffsetY` безвозвратно. Любой слегка наклонный свайп банкует Y.

**Проявляется это телепортом, а не залипанием.** Пришло сообщение → `setNodes` → `layout()` →
`centreSpanX` вырос → `rangeX.start` опустился → камера за кадр уезжает на величину банка. Выглядит
как криво сделанное авто-следование, которое потом загадочно прекращается. Вертикальный вариант
резче: пока содержимое влезает по высоте, `rangeY` вырожден и копит; как только граф получит дорожку
и станет выше вьюпорта, `offset.y` прыгнет с центрирующего значения прямо на зажатый банк.

Отдельно: `isMoved` защёлкивается навсегда (`:126`, сброса нет), поэтому правило покоя «первый узел в
центре» после первого касания не применяется больше никогда, и новые узлы не перецентрируются. Флаг
смешивает два смысла — «пользователь взял управление» и «`rawOffset` засеян», — а для инерции нужен
третий: «камерой управляет анимация».

Проверено попутно: пустой диапазон невозможен ни у `timelinePanRangeOf`, ни у `panRangeOf`, поэтому
`coerceIn` на записи не бросит.

### Что сделает затухание, если этого не починить

`pan()` возвращает `Unit`, то есть у анимации нет ни одного признака, что дельта отвергнута.
Платформенный fling гасится ровно сравнением запрошенного с потреблённым
(`DefaultFlingBehavior.performFling`: `if (abs(delta - consumed) > 0.5f) this.cancelAnimation()`).
Этого сигнала здесь физически нет, поэтому затухание доработает свою длительность целиком, кормя
`pan()` за границей: **один резкий флик забанкует несколько тысяч пикселей мёртвой зоны там, где
палец банковал сотни.**

**Отладочная панель этого не покажет — и это надо починить вместе.** Строка `pan` будет тикать с
частотой кадров, но не покраснеет: `FRAME_LIMIT = 140` (`GraphTelemetryMappers.kt:59`) выше 120 Гц. А
`layer` покажет ≈0/s, потому что пересчёт `offset` даёт структурно равный `Offset` и читателя в
`graphicsLayer` не инвалидирует. По той же причине встанут `edges`, `backdrop`, `overlay` и строка
`camera`. Отпечаток «анимация молотит в стенку» — это `pan ≈ fps` при `layer ≈ 0`, и сейчас панель
его не различает. Плюс `lastPan` перетирается дельтами затухания, так что строка `last pan` после
каждого флика вырождается в «0, 0».

## Ловушка: покомпонентное затухание гнёт диагональ

Первое, что приходит в голову — `Animatable<Offset, AnimationVector2D>.animateDecay(splineBasedDecay())`.
Это неверно, и вопрос даже не «одна 2D-анимация или две 1D»: **это одно и то же.**
`FloatDecayAnimationSpec.generateDecayAnimationSpec<T>()` даёт `VectorizedFloatDecaySpec`, который
применяет float-спеку к каждой оси отдельно и берёт `maxOf` по длительностям. KDoc не оставляет
трактовок: *«by applying the given `FloatDecayAnimationSpec` on every dimension»*.

Прямая траектория получается ⟺ путь по оси линеен по начальной скорости. У экспоненты
`s(v,t) = v·(e^{ft}-1)/f` — множитель выносится, **покомпонентная экспонента прямую не гнёт**
(проверено численно: бросок 30°, `y/x = 0.577350269` на всём интервале, ровно `tan 30°`). У spline
`n = 1.736 ≠ 1` и `m = 0.736 ≠ 0`, и ломаются оба условия.

**Конечная точка уходит с направления броска**: `θ_end = atan((tan θ)^1.7362676)`. Плотность сюда не
входит, искажение чисто геометрическое.

| Бросок | Прилёт | Увод |
|---|---|---|
| 10° | 2.81° | 7.19° |
| **22.15°** | 11.86° | **10.29° — максимум** |
| 30° | 21.07° | 8.93° |
| 45° | 45.00° | 0° |
| 60° | 68.93° | −8.93° |

Инвариантны только 0°, 45° и 90°; всё остальное присасывается к ближней оси.

**И траектория выгибается, а в конце ломается в крючок**, потому что длительности осей разные
(`Ty/Tx = (tan θ)^0.736`): после `min(Tx, Ty)` одна ось стоит, а вторая ещё едет.

| Бросок | Доля fling'а по одной оси | Макс. отклонение от хорды |
|---|---|---|
| 10° | 72.1 % | — |
| 15° | — | 22.7 px (3.9 %) |
| 30° | 33.3 % | **28.8 px (5.6 %)** |
| 45° | 0 % | 0 |

На полотне это читается как «дёрнул по диагонали, а оно доехало горизонтально».

## Как это решает сама платформа

В foundation есть `Modifier.scrollable2D` со `Scrollable2DState`, и он **покомпонентно не затухает**.
`ScrollingLogic2D.doFlingAnimation` сводит скорость к модулю, гоняет через **одномерный**
`FlingBehavior` и раскладывает скалярную дельту по **зафиксированному на отпускании** углу:

```kotlin
fun Offset.toMagnitudeFloat() = sqrt(x.pow(2) + y.pow(2))
fun Float.toDecomposedOffset() =
    if (available.angle.isNaN()) Offset(0f, this)
    else Offset(x = abs(cos(available.angle) * this) * sign(available.x),
                y = abs(sin(available.angle) * this) * sign(available.y))
// …
private val Velocity.magnitude get() = sqrt(x.pow(2) + y.pow(2))
private val Velocity.angle     get() = atan2(x = x, y = y)
```

Отсюда: траектория строго прямая по направлению отпускания для всех 360°; пролёт и длительность равны
одномерным, то есть таблице выше без поправок на угол; спецкейсов нет, кроме защиты
`angle.isNaN()`. Работает это ещё и потому, что `magnitude ≥ 0`, значит скалярная анимация монотонно
растёт от нуля и сравнение `abs(delta - consumed) > 0.5f` корректно — знаки живут только в `sign()`.

`Velocity.magnitude` и `Velocity.angle` **приватные**, так что руками их пришлось бы переписать.

Код выше прочитан в 1.10.6 и **перепроверен в 1.10.0** — той версии, которая реально разрешается:
`doFlingAnimation` (`Scrollable2D.kt:398`), `toMagnitudeFloat` (`:402`), `toDecomposedOffset` (`:408`),
возврат `consumedOffset.toMagnitudeFloat()` (`:451`), `magnitude`/`angle` (`:519-522`) — совпадает
дословно. Гашение на границе в 1.10.0 — тоже единственный механизм `abs(delta - consumed) > 0.5f`
(`Scrollable.kt:1054`): развилки `isFlingContinuationAtBoundsEnabled` / `shouldCancelFling`, живой в
1.9.5, здесь уже нет. `minimumFlingVelocity` в foundation 1.10.0 не встречается ни разу.

**Проверяемое утверждение для юнит-теста:** для любого угла отпускания отношение накопленных
смещений `dy/dx` постоянно на всём интервале и равно `vy/vx`. Покомпонентная реализация этот тест
провалит, скалярная пройдёт.

### Опасность: foundation приходит транзитивно

**BOM в проекте нет, и `androidx.compose.foundation` не объявлен нигде** — ни в каталоге, ни в
бандле `android-ui`, ни в одном `build.gradle`. Версии прибиты руками: `compose = 1.11.4`,
`material3 = 1.4.0`. Разрешается при этом так:

```
androidx.compose.foundation:foundation-android:1.10.0   ← транзитивно через material3 1.4.0
androidx.compose.animation:animation-android:1.11.4
androidx.compose.ui:ui:1.11.4
```

То есть **foundation 1.10.0 при остальном 1.11.4**, и на 1.10.0 его держит только констрейнт
material3. Если инерция опирается на API foundation, напрашивается объявить её в каталоге и в бандле
`android-ui`, чтобы foundation ехала вместе с остальным.

**Осторожно: `version.ref = "compose"` здесь ломает сборку.** Судейство проверило по кэшу, и
foundation 1.11.4 **не существует**: модуль `animation:1.11.4` из того же релиза зависит на
`foundation-layout:1.10.0`, а `ui:1.11.4` несёт на foundation не зависимость, а constraint `1.7.0`
с причиной «prevents a regression in Overscroll». Список версий, которые Gradle вообще видел,
у runtime / ui / animation доходит до 1.11.x, а у foundation и foundation-layout **обрывается на
1.10.6**. То есть foundation и остальной Compose в этом релизе намеренно живут на разных линиях.
Объявлять — только явной версией (`composeFoundation = "1.10.6"` либо «1.10.0», чтобы
зафиксировать текущее поведение), и помня, что бандл `android-ui` уходит через `api` из `core/ui`
во всё приложение.

Резолв на момент записи (`:feature:chronology:ui:dependencies --configuration debugCompileClasspath`):

```
androidx.compose.foundation:foundation:1.8.1 -> 1.10.0
androidx.compose.animation:animation:1.10.0 -> 1.11.4
androidx.compose.ui:ui:1.10.0 -> 1.11.4
```

Смешение версий, о котором предупреждает этот раздел, **уже происходит** и не требует нашего участия:
foundation 1.10.0 сама просит animation и ui версии 1.10.0, а исполняется с 1.11.4.

Путь «руками» (`VelocityTracker` + `splineBasedDecay` + `Animatable`) целиком лежит в
`animation`/`animation-core`/`ui` 1.11.4 — объявленных и версионированных верно.

## Ловушка, которой не было в разведке

Разведка рекомендовала `scrollable2D` и отдельным пунктом советовала взять к нему
`rememberOverscrollEffect()` — «двумерно из коробки». Судейство показало, что на **этом** экране эти
две вещи вместе не работают.

`applyToFling` снимает скорость на релаксацию растяжения **до** запуска инерции
(`AndroidOverscroll.android.kt:703-719`), а `absorbToRelaxIfNeeded` устроен по принципу
всё-или-ничего (`EdgeEffectCompat.android.kt:74-88`):

```kotlin
return if (flingDistance <= actualDistance) {
    onAbsorbCompat(velocity.roundToInt()); velocity   // ← съедает ВСЮ скорость оси
} else 0f
```

Дальше цепочка замыкается на дефекте, который этот же документ описывает выше. При одной дорожке
`panRangeOf` вырожден, ось Y не потребляет ничего, значит на каждом кадре драга весь вертикальный ход
уходит в растяжку — **вертикальный край растянут после любого свайпа**. Отпускаем под углом:
если `flingDistance(vy)` меньше глубины растяжки, **весь `vy` съедается**, и `available` становится
`(vx, 0)` — угол скачком превращается в 0°.

| глубина растяжки | `vy` ниже этого съедается целиком |
|---|---|
| 10 dp | 181 dp/s |
| 100 dp | 682 dp/s |
| 300 dp | 1284 dp/s |

Бросок 30° при 2000 dp/s даёт 504 dp за 831 мс с растянутым краем и 561 dp за 924 мс без него —
**разрыв 11.2 % по пути и по времени от невидимого состояния**. Требование «на 360» при этом не
выполняется: угол не уводит на градус, а защёлкивается на ось. (На API ≤ 30 `distanceCompat == 0f`,
и дефекта нет.)

Вывод, ради которого это записано: **растяжение у края и требование «360» на этом экране
конфликтуют.** Overscroll здесь придётся либо не брать, либо брать так, чтобы он не участвовал в
`applyToFling`. То есть главное преимущество `scrollable2D` над путём «руками» — «overscroll
бесплатно» — на этом экране не бесплатно.

## Решение

**Своя скалярная физика:** `VelocityTracker` + `splineBasedDecay<Float>` + `AnimationState.animateDecay`
по **модулю** скорости, с разложением скалярной дельты на угол, зафиксированный на отпускании. Жест
остаётся на `detectDragGestures` — в перегрузке с `orientationLock`, которая отдаёт up-событие.

Итог судейства по трём линзам (0–10, выше лучше):

| | физика | риск | конвенции | сумма | блокирующие |
|---|---|---|---|---|---|
| `scrollable2D` | 7 | 6 | 7.5 | 20.5 | **2** (оба устранимы) |
| **своя скалярная физика** | **9** | **8** | **8** | **25** | **нет** |
| покомпонентное (foil) | 3 | 4 | 5.5 | 12.5 | **3** (одно неустранимо) |

Победа не по сумме, а по правилу вето: подход с блокирующим дефектом по любой линзе не побеждает
даже с высшей суммой. У победителя блокирующих нет ни по одной.

Что за него:

- **Направление держится на всех 360°** — проверено численно, накопленное `dy/dx` против `tan θ`
  расходится не более чем на 3e-05 %, пролёт совпадает со спекой до третьего знака.
- **Тождество, на котором стоит разложение, доказано**: `cos(atan2(vy, vx)) == vx/|v|`, включая
  случай нулевой компоненты. Приватные `magnitude`/`angle` переписывать не надо — они сводятся к
  делению на модуль. На отрицательных дельтах эта форма строго корректнее платформенной, которая
  верна лишь пока скаляр неотрицателен.
- **Критерий границы лучше платформенного**: он смотрит на диапазон, а не на дельту кадра, поэтому
  не спотыкается ни о нулевую дельту первого кадра, ни о точность float на длинной хронике. Угол
  закрывается за один кадр там, где `scrollable2D` нужно два.
- **Ничего приватного в несущей конструкции.** Всё лежит в `animation` / `animation-core` / `ui`
  1.11.4 — объявленных и версионированных верно. Каталог версий не трогается, чужие экраны тоже.
- **Дом-стиль совпадает буквально** — `@Stable` держатель, анимация корутиной, scope параметром,
  как в `PredictiveBackController`.
- **Проверяемость**: вся физика — чистые функции, плюс держатель тестируется на JVM. У соперника
  решающий признак «ведёт затухание» живёт в декораторе и в держателе и юнит-тестом не покрывается.

Чем платим — прямо:

- **Растяжения у края нет.** Это самая крупная потеря, и она реальна: на полотне без скроллбара
  это единственный сигнал «дальше истории нет». Смягчает её только то, что у соперника оно тоже
  оказалось неприменимым (см. ловушку выше), — но у соперника оно хотя бы уже написано.
- **Четыре платформенных решения повторены руками**: порог `> 1f`, кламп по `maximumFlingVelocity`,
  `MotionDurationScale` со scaleFactor 1, терпимость 0.5 px. Тестами ловятся два.
- **Кламп на записи ничем не принуждён.** У соперника контракт лямбды — входной билет; здесь
  единственная страховка — тест, а тест можно удалить.

Почему проиграл `scrollable2D`, хотя разведка ставила на него: два блокирующих дефекта (конфликт с
overscroll выше; правка каталога, целящаяся в несуществующую версию), а из оставшихся плюсов главные
— «overscroll бесплатно» и «nested scroll» — на этом экране либо не работают, либо не нужны: ни
родителя-скроллера, ни ребёнка-скроллера сегодня нет. Остаётся один настоящий: кривая гарантирована
тем же вызовом, что у `LazyColumn` в чате, а не тем, что мы передали правильную спеку. Это довод
сильный, но он не перевешивает необходимость управлять недокументированной эвристикой чужой
библиотеки без единого теста.

Отдельно судейство сняло возражение, которое было записано против пути «руками»: **гонки отмены
нет**. `flingJob?.cancel()` и цикл живут на одном диспатчере, `withFrameNanos` при отменённом job
резюмируется исключением, и ни один кадр затухания не применится после начала нового драга.

### Минимальная перестройка

1. **Вынести диапазон камеры** из выражения внутри `offset` (`GraphCanvasState.kt:87-92`) в чистую
   функцию в `GraphGeometry.kt` от `(centreSpanX, bounds, viewport, isEmpty)`, отдающую оба диапазона
   одной сущностью в `entity/`. Одно определение «где камере можно быть» — и для чтения, и для
   записи, и юнит-тест без Compose.
2. **Вторая чистая функция**: по текущей камере, запрошенной дельте и диапазону вернуть новую камеру
   **и** потреблённую дельту. Это весь контракт инерции, выраженный арифметикой.
3. **`pan()` клампит на записи и возвращает потреблённое.** Правило «наружу только `State<T>`» это не
   нарушает: `pan()` исполняется в корутине жеста или анимации, а не в фазе Compose, поэтому чтение
   `placement`/`viewport` там ни на что не подписывает.
4. **`layout()` пере-зажимает сохранённую камеру** после обновления `viewport`/`placement` — тогда
   хранимое и показываемое не разъезжаются, и телепорты исчезают вместе с банком.
5. **Оставить блок `pointerInput`**, но перевести `detectDragGestures` на перегрузку с
   `orientationLock` и докормить `VelocityTracker`: `onDragStart` — сброс трекера и отмена идущего
   затухания, `onDrag` — точка в трекер и `pan`, `onDragEnd` — up-событие в трекер и запуск
   инерции со скоростью, зажатой по `maximumFlingVelocity`. Приём `pointerInput(Unit)` +
   `rememberUpdatedState` остаётся и продолжает делать свою работу — не отменять жест при входящем
   сообщении.
6. **Цикл затухания в держателе**: скалярный `AnimationState(0f, |v|).animateDecay(spec)`, дельта
   раскладывается на зафиксированный угол, scope приходит параметром (корутина жеста умирает на
   отпускании — см. `PredictiveBackController`). Обязательно `withContext` с
   `MotionDurationScale(scaleFactor = 1f)`: иначе «Animator duration scale» из опций разработчика
   меняет физику, а при значении Off весь пролёт приезжает одной дельтой.
7. **Расщепить телеметрию `pan`** на жест и анимацию, добавить счётчик отвергнутой дельты и признак
   «идёт затухание». Иначе панель не отличит «идёт fling» от «fling молотит в стенку» от «крутится
   цикл», а это её единственное назначение.
8. **`isMoved` разложить**: смысл «сдвиг засеян» исчезает вместе с незажатым сдвигом, «пользователь
   взял управление» остаётся снапшот-полем, а «камерой управляет анимация» в снапшот-состояние
   заводить не надо — за него никто не рисует, панель снимает по таймеру.

### Что стоит знать при любом способе

- **`Animatable.updateBounds` здесь непригоден**, хотя он ровно про границы: он останавливает
  анимацию при достижении границы по **любой** оси (`Animatable.kt:99-118`, `:308-321`), а
  вырожденный `panRangeOf` — норма этого экрана. Наклонный бросок умирал бы на первом кадре.
  Границы придётся держать самому.
- **`cameraRangeOf` берёт границы из раскладки скомпонованных узлов** — и это верно ровно до
  появления виртуализации. Когда полотно начнёт компоновать только видимое, границы камеры поедут
  вместе с камерой. «Протяжённость всего графа» и «что сейчас в композиции» надо развести до, а не
  после; сегодня они совпадают случайно.
- **`getScrollFriction()` делает платформенную кривую недоступной юнит-тесту** — это top-level
  `val`, читаемый при инициализации класса. Тесты гоняются на `exponentialDecay` и проверяют
  структуру (прямая, останов, скольжение), а саму кривую сверяет владелец на устройстве.

## Решения, которые надо принять явно

**Диагональ, упёршаяся одной осью.** `scrollable2D` сворачивает потреблённое в **модуль**
(`consumedOffset.toMagnitudeFloat()`), поэтому диагональный fling, у которого упёрлась только одна
ось, гасится целиком: бросок влево-вниз, доехавший до левого края при живом запасе снизу,
останавливается насмерть, а не съезжает вдоль края.

На этом экране это не краевой случай, а норма: при одной дорожке ось Y вырождена и не потребляет
ничего, значит естественный слегка наклонный флик может умирать мгновенно. Развилка — считать дельту
на оси без запаса **поглощённой** (инерция жива, идёт вдоль стенки, как в списке) или **отвергнутой**
(встаёт целиком, как у платформы). Требованию «360» отвечает первое: гасить, только когда обе оси не
потребили ничего. Это отход от платформы — значит решение с записанной причиной, а не побочный эффект
реализации. Место решения — чистая функция из пункта 2, там же и тест.

**Решение принято в пользу «поглощённой», но с оговоркой, которой не было в первой редакции.**
Судейство измерило цену на вырожденной оси: скольжение вдоль стенки длится полную длительность
броска, а проезжает только проекцию. При 2000 dp/s и одной дорожке это 645 dp при 5°, 561 dp при
30°, **324 dp при 60° и 112 dp при 80° — и все за 924 мс**. Восемьдесят градусов означают почти
секунду ползания со средней скоростью 122 dp/s, что читается уже не как инерция, а как заедание.
Решение верно для пологих бросков и сомнительно круче 60°; если на устройстве это подтвердится,
правится одним оператором (`&&` → `||`) либо угловым порогом. Обратный ход дешёвый — это и есть
причина принять решение сейчас, а не гадать.

**Растяжение у края.** Первая редакция советовала взять его «из коробки» вместе с `scrollable2D`.
**Отменено:** см. «Ловушка, которой не было в разведке» — на этом экране overscroll съедает
вертикальную скорость целиком и ломает требование «360». В выбранном решении растяжения нет вовсе,
и это осознанная потеря, а не упущение. Вернуть его можно руками — `OverscrollEffect` публичен
(`Overscroll.kt:55-56`), — но это два контракта (`applyToScroll`, `applyToFling`) и самостоятельное
выставление `source`, от которого зависит, применится stretch или нет. Отдельной задачей, после
того как инерция ляжет в руку.

**Токен затухания.** В `AppMotion` все токены — `tween`, ни одного decay или spring. При этом
`decelerate` (`AppMotion.kt:111`) заведён с KDoc «Без разгона… **Для камеры на полотне**», а
`largeTween()` — «перелёты камеры, стягивание линии». То есть дизайн-система про эту камеру уже
знает, а `DecayAnimationSpec<Float>` дома не имеет. Завести `flingDecay()` в `AppMotion` —
согласованный ход; по `.claude/rules/workflow.md` новый **токен** одобрения владельца не требует, в
отличие от нового правила.

## Дом-стиль, которому надо соответствовать

Образец держателя с корутинной анимацией — `core/routing/.../PredictiveBackController.kt`:
`@Stable` класс, анимируемые значения полями, снапшот-поля с `private set`, служебные счётчики
обычными полями, приём жеста — `suspend fun`, который только `snapTo`, а **финальная анимация
принимает scope параметром и не владеет им** (`:116-127`, `:140-145`). Причина в KDoc `:21-22`:
корутина жеста отменяется на отпускании, поэтому доигрывать надо в другой. Это ровно ситуация
инерции.

Соседа, которого нельзя задеть, зовут `PredictiveBackHandler` (`PredictiveNodeHost.kt:119`):
горизонтальный жест у левого края экрана съедает системный «назад», а не полотно. Значит нельзя
рассчитывать, что жест увидит все горизонтальные драги, и `change.consume()` (`GraphCanvas.kt:71`)
обязан остаться.

Тесты — JUnit 5, имена предложением в бэктиках. В бандле `unittest` **нет** ни compose-ui-test, ни
Robolectric, и `GraphCanvasStateTest` не существует. То есть арифметика инерции обязана быть чистой
функцией, чтобы вообще быть проверяемой.

## Тесты, которые надо написать

Арифметика камеры:

- `consumed delta equals the request while the camera has room`
- `consumed delta is truncated at the boundary`
- `consumed delta is zero on a saturated axis`
- `a degenerate range consumes nothing` — вырожденный диапазон это норма экрана, не краевой случай
- `a rejected delta cannot be banked for later` — уехать в стенку на 3000, вернуться на 100, камера
  обязана сдвинуться ровно на 100. Это дефект из раздела выше, выраженный без Compose
- `banked overshoot cannot outlive a layout pass` — сторож против телепорта при расширении диапазона

Разложение направления:

- `a diagonal fling keeps its direction` — `dy/dx` постоянно и равно `vy/vx` на всём интервале
- `the decomposition matches the platform angle formula` — сетка по четырём квадрантам против
  `abs(cos(atan2(vy, vx)) * d) * sign(vx)`. Писать **с допуском** (1e-4 px хватит): на точном
  равенстве float падает
- `a zero velocity has no direction`, `a NaN velocity has no magnitude`

Цикл затухания и держатель:

- `a fling survives a wall while the other axis has room` / `a fling dies when the only live axis
  hits its wall` — две половины принятого решения о развилке
- `a fling ignores the system animation duration scale` — сторож против мины, которая иначе видна
  только на устройстве с включённой опцией разработчика
- `a new touch cancels the running fling`
- `a layout pass re-clamps the stored camera`

## Что проверять на устройстве

Эмулятора у агента нет, визуальную проверку делает владелец.

- **Опции разработчика → Animator duration scale.** Выключить и включить обратно: инерция полотна
  обязана вести себя одинаково и одинаково со списком в чате. Единственная проверка, которая ловит
  забытый `MotionDurationScale`; без неё дефект доживёт до первого пользователя, у которого анимации
  урезаны ради батареи.
- **Крутой наклонный бросок при одной дорожке** — 60° и 80°. По расчёту это 324 dp и 112 dp за одни
  и те же 924 мс; если ощущается как заедание, развилка «поглощать/отвергать» правится одним
  оператором.
- Медленный флик не должен ощущаться как «палец отпустил, а оно не поехало»: своего порога скорости
  заводить не надо, платформенный барьер `abs(v) > 1f` — защита от `ln(0)`, а не UX-порог, и при
  137 dp/s spline пролетает 2.9 px за 61 мс, то есть кривая сама делает слабый флик невидимым.
- Диагональный бросок под 30° должен доезжать под 30°, а не под 21°.
- Флик по диагонали в угол — поведение сверить с принятым решением выше.
- В панели в покое: `pan` и `layer` по нулю. Во время затухания: `pan` и `layer` тикают **вместе**;
  `pan` при стоящем `layer` — это и есть «молотит в стенку».
- После упора в край жест обратно должен отвечать сразу, без мёртвой зоны.
- Проверить пролёт по таблице спеки: 1000 dp/s ≈ 194 dp за 555 мс. Забытый `Density` даёт ×2.106 и
  по пути, и по времени.

## Что осталось непроверенным

- **`ViewConfiguration.getScrollFriction() == 0.015f`** — из AOSP по памяти, на диске не подтверждено:
  `android.jar` содержит только stubs. Единственный факт разведки, оставшийся непроверенным.
- **Одноосное гашение диагонали** выведено из чтения `doFlingAnimation` и структуры байткода —
  требует проверки на устройстве.
- **Цена скольжения вдоль стенки на крутых углах** посчитана, но не прожита руками: 80° → 112 dp за
  924 мс. Проверять вместе с решением о развилке.
- **Существует ли foundation новее 1.10.6** — по кэшу нет, но опросить Google Maven из сессии не
  удалось (сеть закрыта). Проверяется одним sync на машине владельца, если понадобится объявлять
  foundation явно.
- **Набросок теста на `BroadcastFrameClock`** в предложенном виде не запустится: `runTest` даёт
  `StandardTestDispatcher`, корутина не стартует до первого `runCurrent()`, и цикл
  `while (clock.hasAwaiters)` не выполнится ни разу — тест не упадёт, а **повиснет** до таймаута.
  Лечится вызовом `runCurrent()` до цикла. Приёма в репозитории нет ни разу, так что первый такой
  тест придётся отлаживать, а не писать по образцу.

## Источники
